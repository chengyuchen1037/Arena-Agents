## 被 v0.12.1 取代或修订的决策

v0.12.1 的原则是“引擎不替用户省钱”（见 [v0.12.1-plan.md](v0.12.1-plan.md) 第 0、1 节），因此改变了本方案里的一部分决策和内容。下表按本文的顺序，列出被**取代**、**修订**、**删除**，或者虽然仍然成立但需要**补充**的地方；“取代它的决策”是 [v0.12.1-plan.md](v0.12.1-plan.md) 第 1 节的 E1–E26（实现记录见该文第 12 节）。正文里对应的位置已在行末标注“（v0.12.1 已修订：E#）”或“（v0.12.1 已补充：E#）”，原文没有改动。

| D13（§0）：`free` 模式下，玩家在新消息到达后防抖约 1.5s 才被唤醒；每人有条数上限，可以选择 `wait` | **取代**：没有防抖，也没有“只放进缓冲、不唤醒”的消息——每条送达的消息（发出者本人除外）都立刻唤醒收件人；Worker 正忙时，期间到达的消息在下一轮边界合并成一次注入。自由讨论的 `debounce_s` 已删除。`wait` 由 `sleep(seconds?)` 取代。每人的条数上限（`max_messages_per_member`）仍然有效 | E1、E3 |
| D21（§0）：人工只能点暂停或继续，暂时不提供人工向 agent 注入消息 | **补充**：原意不变——仍然不能向 agent 注入消息。但用户能做的事多了：为**本局**设置 token / 费用上限，并可勾选“达到上限后强制停止”（用量到 100% 时自动暂停，原因 `budget`）；开局前编辑名册（名字、头像、性格设定、记忆）；终局后手动“复盘” | E10、E22（另见 E14、E16、E21） |

| §1 目标 6、§8：信息流只显示发言（`message.committed`），整条渲染 | **补充**：除发言、公告、能力宣言、质询与回复外，信息流还显示**请求卡片**——问题、收件人、倒计时；组内可见的请求实时显示每人当前的选择；关闭后显示结果与计票。上帝视角看全部请求，玩家视角只看与自己有关的 | E18（另见 E25） |
| §3.1：每个 agent 一个 asyncio 任务，主循环是 `await mailbox.get()` | **修订**：Actor 不再有常驻任务和收件循环（`app/runtime/mailbox.py` 已删除）：`Agent.deliver(envelope)` 把信封放进 `pending`，休眠中的 agent 用 `loop.call_soon` 安排**一次**激活——同一次同步泵里投递的所有信封合成一次激活；任务只在“一次运行”（Worker）期间存在。Actor 仍然不调用 LLM、不做慢 I/O | E1（实现见契约 §10.2 第 1 条） |
| §3.1 唤醒和取消策略表：URGENT / NORMAL / AMBIENT 三级；NORMAL 防抖约 1.5s 后唤醒，AMBIENT 只放进缓冲；URGENT 取消后重启，发言权被收回时只取消、不重启 | **取代**：优先级只剩 `urgent` / `normal`，`urgent` 只表示“期望收件人采取行动”，仅用于唤醒原因的排序。**所有**送达的信封都立刻唤醒收件人（发出者本人除外）；Worker 正忙时，期间到达的信封在下一轮边界合并成**一条**注入（在途合并，沿用）。取消只由 `interrupt=True`、且命中本次运行焦点（频道或请求）的信封触发；取消后立刻带着全部待处理内容重新激活（发言权被收回时也一样，不再“只取消、不重启”）。防饥饿（连续取消 2 次后改为注入）和 `gen_id` 不变。**已出局**的玩家不被广播类消息唤醒，只被直接发给他的事件（他的请求、发言权、系统私聊）唤醒 | E1、E7、E23 |
| §3.1：被取消时，为未完成的 tool_call 合成一条“已中断”结果，保证 tool_call_id 成对 | **取代**：被取消或已过期的那次模型调用**直接丢弃，不写进会话**。assistant 消息和它的全部工具结果在没有任何 `await` 的一段里一起追加，取消因此不会留下不成对的 tool_call，也不需要合成“已中断”结果 | E7（会话见 E5） |
| §3.2、§6：Worker 保留调用预算；“每个 agent 有调用预算”（v0.12.0 的实现是按执行深度取值的每次运行轮数上限 `max_rounds`，见契约 §3.2） | **删除**：没有轮数上限，也没有“执行深度”（界面的下拉框和 `config.yml` 的 `max_rounds` 一并删除）。一次激活内 Worker 可以无限轮“模型调用 → 工具”，直到调用 `sleep`；模型不调用任何工具时，视为不定时休眠。引擎内部没有费用熔断，唯一的刹车是用户设置的 token / 费用上限；模型的思考深度仍在绑定里按角色设置 | E4、E10 |
| §3.3：每次唤醒都重新构建上下文（状态板 / 记忆 / 可见历史 / 本次唤醒），只有同一次唤醒内的多轮调用沿用同一份对话 | **取代**：每个 agent 在整局里有一份**只追加**的持久会话：system 与 tools 在创建后逐字节不变，供应商的前缀缓存才能命中。第一次激活发完整的开局消息（§3.3 的状态板 / 记忆 / 可见历史布局现在只用于它），之后每次激活只追加增量——新条目、状态板的**变化部分**和唤醒原因；没有新东西可说就回到休眠，不调用模型。暂停→继续沿用同一份会话；新局、导入、从存档恢复时清空（会话不进存档，恢复后按账本重建一次） | E5 |
| §3.3：`system = 角色设定 + 剧本规则正文 (+ 主持人：主持人手册 + 工具说明)` | **补充**：system 里另有名字和编号（`N3 Carol`）、该玩家的**性格设定**和**长期记忆**（来自名册；内容为空、或本局关闭了“加载记忆”时，整段省略）。它们都在不变的前缀里，因此可以被缓存 | E16（另见 E13、E24） |
| §3.3：压缩沿用 `compact_context`；上下文接近窗口上限时，引擎在状态板里提醒 agent 压缩 | **取代**：由编排触发——每次模型响应后，按真实 token 数（未命中缓存 + 缓存读取 + 缓存写入）计算会话大小；达到该模型上下文窗口的 60%（`compact_at`）时，在会话里追加一条提醒，请 agent 调用 `compact_context`（生成摘要并重建会话，一次压缩只造成一次缓存失效）；到 90%（`trim_at`）仍未压缩，就从最前面按完整的轮裁剪。压缩后的会话只有又增长了窗口的 10% 才会再次提醒。agent 也可以主动压缩 | E6 |
| §4.2：`open_request(to, kind, question, options, duration_s, sealed, default)`；收齐或到时后，引擎关闭请求并唤醒主持人 | **补充**：新增 `share_answers`（收件人和主持人实时看到彼此当前的答案，可随时改答；与 `sealed` 互斥）和 `auto_close`（`all_answered`：全员作答即关闭，是默认值；`unanimous`：全员作答且答案一致才提前关闭，否则开到截止，期间可以改答；`deadline`：只在截止时关闭）。“收齐即关闭”现在只是默认行为 | E25（用途见 E19） |
| §4.3、§8 等：玩家编号 `p01`–`p12`（例如“🗳️ p03 → p05”） | **取代**：内部 id 为 `N1`–`N12`（编号即座位号），默认名字 Alice、Bob、…、Leo。给模型看的文本写作 `N3 Carol`（工具参数用 id，说话用名字），界面上只显示名字 `Carol`。名字、头像、性格设定和记忆按座位保存在工作区的名册里，跨对局不变 | E13、E14 |
| §5：玩家工具 `wait()`——本次唤醒什么也不做（D13、§6 也提到 `wait`） | **取代**：`sleep(seconds?)`，玩家和主持人都有。不带参数：休眠到有新消息或新状态为止；带 `seconds`（1–3600 游戏秒）：到点即使没有新消息也会醒来，便于自主规划（暂停时定时器冻结）。模型不调用任何工具时，视为不定时休眠。`wait` 只作为不公布的别名保留 | E3 |
| §6：`paused` 的进入方式——用户暂停或强制暂停、主持人 `hold_game`、出错 | **补充**：多一种进入方式：达到用户设置的预算上限、并且勾选了“达到上限后强制停止”时自动暂停（`pause_reason` 为 `budget`），提高上限或取消勾选后才能继续。看门狗不再触发暂停。暂停时所有 agent 都显示为休眠，它们的持久会话保留 | E10（另见 E2、E5、E9） |
| §6：LLM 闸门——全局和每个 Provider 各有一个 Semaphore | **修订**：并发闸门默认不限（`llm_concurrency`、`llm_concurrency_per_provider` 默认 `0`），只用来应对 Provider 的速率限制（429 时退避重试），不用来省钱；每次调用的超时照旧 | E8 |
| §6：看门狗——对局静止时唤醒主持人；连续 N 次唤醒都没有推进，就自动 `hold_game` | **修订**：看门狗仍然只唤醒主持人，但**不再自动暂停**；连续唤醒仍无进展时，只在界面上显示警告横幅（`stall_notice`），由用户决定是否暂停；账本重新推进后横幅自动消失 | E9 |
| §7、§13 M4：`SESSION_SCHEMA_VERSION = 3`；存档含 Ledger、世界状态、笔记与压缩摘要、用量 | **取代**：存档格式 v4（`SESSION_SCHEMA_VERSION = 4`）：用量分四类 token；另存本局的预算、名册快照（名字、头像、性格设定、记忆，含主持人头像）和“本局加载记忆”开关；**不保存持久会话**。v0.12.0 的存档（`p01` id、旧计费字段）不能打开，保留在存档列表里、文件不被修改（与 D3 一致） | E20（另见 E5、E10、E11、E14、E24、E26） |
| §8：`agent.status` 的 `state: idle/thinking/acting/stopped` | **取代**：只有三种状态 `thinking` / `acting` / `sleeping`；“空闲”“已停止”不再作为状态，对局暂停或结束时所有 agent 都显示休眠，对局状态另有标识。载荷为 `{id, state, until}`，`until` 是定时休眠的结束时刻（游戏时钟秒，没有定时为 `null`） | E2、E3 |
| §8：`agent.metrics` 的 `{id, llm_calls, thinking_rounds, tool_calls, rejections, tokens_in, tokens_out, cost}` | **取代**：用量区分四类 token（未命中缓存的输入、缓存读取、缓存写入、输出）和四个价格；载荷为 `{id, activations, calls, prompt_tokens, cache_read_tokens, cache_write_tokens, completion_tokens, cost_usd, tool_calls, thinking_rounds, rejections, cache_hit_rate}`，其中 `prompt_tokens` 现在只指未命中缓存的输入 | E11（激活次数见 E1） |
| §8 事件表：请求只有 `request.opened` / `request.progress` / `request.closed`，没有预算、名册、复盘事件 | **补充**：新增 `request.answer`（`share_answers` 请求里的每次作答）、`budget.updated` / `budget.warning` / `budget.reached`、`roster.updated`、`review.progress`；`request.closed` 增加 `result`。PublicSession 升到 v3（`schema_version` 为 4）：去掉 `execution_depth`，新增 `budget`、`memory_enabled`、`review`、`stall_notice`，参与者带 `avatar` 和 `sleep_until`。详见契约 §10.6 | E10、E14、E18、E21、E25 |
| §9：`app/runtime/` 的文件列表（含 `mailbox.py`；§12、§13 M2 也提到“邮箱”） | **修订**：`mailbox.py` 已删除（E1），新增 `conversation.py`（持久会话，E5）；其余实际布局以契约 §1、§3.1、§10.2 和代码为准 | E1、E5 |

| §14：风险“上下文过长”——每次唤醒都重新构建，提醒 agent 压缩；“成本暴涨”——普通消息默认不唤醒、主持人对 `free` 讨论只做 AMBIENT 处理、设置预算和并发闸门 | **取代**：不再靠“少唤醒”省钱——每条消息都唤醒相关 agent，调用量和 token 比 v0.12.0 高一个数量级，这是刻意的设计；token 靠持久会话加前缀缓存、在途合并和按需压缩来管理，并发闸门默认不限，花多少钱由用户设置的上限决定 | E1、E5、E6、E8、E10 |

## 0. 决策记录

| # | 决策 |
|---|---|
| D1 | 主持人是**独立 agent**，**不能操控其他 agent 的内部进程**（不能取消、读取或注入别人的 Worker）；**不能修改已发生的事**：Ledger 只追加，更正必须写成新条目 |
| D2 | **流程由 LLM 主持人驱动**：轮流发言靠主持人发公告并管理发言权，具体方法写在提示词和剧本手册里 |
| D3 | **不兼容旧存档**。删除 legacy moderator、session migration 和 workflow DSL |
| D4 | 支持切换观战视角：上帝视角，或任意一名玩家的视角 |
| D5 | 思维链和工具明细**只写进日志**，前端不展示 |
| D6 | 公告用**混合方式**：敏感公告必须用模板，其他公告可以自由撰写 |
| D7 | **玩家状态可以改写**（包括复活）。这是主持人通过状态工具做的“向前修改”，历史不变 |
| D8 | **由主持人判定终局**。`end_game` 后所有 agent 停止；UI 点“继续”可以恢复 |
| D9 | **由引擎发牌**；主持人另有随机数工具，每次抽取都记入 Ledger |
| D10 | **硬约束尽量少**：引擎只保证通用的物理规则 |
| D11 | 日志用**明文** JSONL，单个文件有大小上限，超过后滚动 |
| D12 | **频道只能由主持人创建**；主持人默认是所有频道的成员 |
| D13 | `free` 模式下，玩家在新消息到达后防抖约 1.5s 才被唤醒；每人有条数上限，可以选择 `wait`（v0.12.1 已修订：E1、E3） |
| D14 | 时限只用**固定时长**。因为 token 生成很快，另外**限制字数**：单条上限，以及每次获得发言权后的总字数上限 |
| D15 | 模板是**通用的结构化消息**，主持人和玩家都能用，每个模板声明谁能使用；“警长归属”加入模板 |
| D16 | 主持人用哪个模型，由现有的 Provider/模型绑定 UI 管理；剧本模式下，主持人的绑定必填 |
| D17 | 开发环境沿用项目现有的 Python 3.12 工具链（与 CI 和 Dockerfile 一致；本机用 uv 提供的 3.12.13） |
| D18 | **暂停时计时器不走**：暂停时冻结剩余时间，恢复后接着计时 |
| D19 | **超长发言会被截断，不会被拒绝**。回执里告诉 agent 截掉了多少字 |
| D20 | **自由讨论不会自动关闭**：时间或字数用尽时，引擎只通知主持人；主持人询问、协商之后，再执行 `close_floor` |
| D21 | **人工只能点暂停或继续**，暂时不提供人工向 agent 注入消息（v0.12.1 已补充：E10） |
| D22 | **质询不限次数**。如果有玩家“骚扰”主持人，主持人可以把该玩家的私聊频道设为 `closed` 作为惩罚，之后也可以重新打开 |
| D23 | 开局时**由引擎自动为每名玩家建立系统私聊** `dm-{id}`（成员为该玩家和主持人）。这是 D12 的唯一例外：主持人可以关闭它，但不能删除 |
| D24 | **身份由引擎告知**：发牌后直接写入每名玩家的状态板（本人的 tag 和属性），不经过主持人。队友关系等规则信息由主持人在建频道时公告 |
| D25 | **能力触发后，引擎冻结相关频道的发言权**。其他玩家收到“发言权被收回”（URGENT）后，由各自的 Actor 取消正在进行的思考；竞态中提交的发言会被 `NO_FLOOR` 拒绝（v0.12.1 已修订：E1、E7） |

## 1. 目标与非目标

**目标**
1. 13 个 agent（12 名玩家 + 主持人）都采用 **Actor（前端）+ Worker（后端）** 结构：Actor 随时收件、随时输出，不会被思考或工具执行阻塞。
2. 主持人用工具驱动整局游戏；引擎与具体游戏无关；规则写在剧本里。
3. 发言权由主持人管理；没有发言权时，引擎返回“无发言权”的回执。
4. 可见性**只由频道决定**；agent 可以在自己有写权限的任意多个频道发言。
5. 玩家可以随时**私聊质询主持人**。
6. 前端：极简的玩家块；信息流只显示发言，并且整条渲染；观战视角可切换。（v0.12.1 已修订：E2、E13、E15、E17、E18）

**非目标**：多进程或分布式运行；真人玩家（协议上预留）；新增游戏剧本（只迁移 `werewolf_12p`，另加一个测试用的最小剧本）；人工消息注入。

## 2. 三层职责

| 层 | 负责 | 不负责 |
|---|---|---|
| **引擎（物理层）** 确定性代码，不含任何游戏词汇 | 频道与成员、发言权（模式、令牌、时长、字数）、请求（截止、密封）、模板参数校验、能力配额、提交闸门、Ledger、调度与计时、存档、日志 | 判断谁该发言、谁出局、是否终局 |
| **剧本** 一个 Markdown 文件 | 开局配置、规则文本、主持人手册、模板、能力、检查函数（只作辅助）、默认限额、可选的硬约束 | 流程编排 |
| **主持人 agent** LLM，Actor + Worker | 读规则、推进流程、建频道、管理发言权、发请求、裁决、改玩家状态、公告、处理质询、宣布终局 | 修改历史、操控其他 agent、绕过提交闸门 |

三道保险：
1. **引擎物理规则**：主持人想违规也做不到。
2. **玩家质询**：发现规则执行有误可以当场指出。
3. **人工暂停或继续**：主持人调用 `hold_game` 时进入暂停，由人决定何时继续。

## 3. Agent 运行时

### 3.1 Actor（前端，永不阻塞）

- 每个 agent 一个 asyncio 任务，主循环是 `await mailbox.get()`。Actor **不调用 LLM，也不做慢 I/O**。（v0.12.1 已修订：E1）
- Actor 维护未读缓冲、待办请求和自己的发言权概览，并决定如何唤醒、注入或取消**自己的** Worker。
- 唤醒和取消策略：

| 优先级 | 玩家的触发条件 | 主持人的触发条件 | Worker 空闲时 | Worker 运行中 |
|---|---|---|---|---|
| URGENT（v0.12.1 已修订：E1、E7、E23） | 获得发言权；收到发给自己的请求；被 @；收到私聊或质询回复；发言权被收回；请求被取消 | 收到质询；能力被发动；队列跑完；请求关闭；自由讨论到时或字数用尽；看门狗报告静止；游戏开始、继续或恢复 | 立即唤醒 | 取消后重启（发言权被收回时只取消、不重启） |
| NORMAL（v0.12.1 已修订：E1，不再防抖） | 自己所在的 `free` 频道有新消息 | 自己持有的 `turn` 发言权被释放 | 防抖约 1.5s 后唤醒 | 在下一轮边界注入 |
| AMBIENT（v0.12.1 已修订：E1，该级别已取消，这些消息现在也立刻唤醒） | 其他消息 | 普通发言（包括 `free` 讨论中的发言） | 只放进缓冲 | 在下一轮边界注入 |

- 防饥饿：连续被取消 2 次后，下一次改为注入。
- 每次唤醒带一个 `gen_id`，晚到的旧结果直接丢弃。
- 被取消时，为未完成的 tool_call 合成一条“已中断”结果，保证 tool_call_id 成对。（v0.12.1 已修订：E5、E7）
- **注入**：Worker 每完成一轮 LLM 调用，就取出 `drain_new()` 的增量，作为一条 user 消息追加进去，再继续下一轮。

### 3.2 Worker（后端，可取消）

- 由 `ParticipantTurn` 演化为 `AgentWorker.run(wake)`：多轮“LLM 调用 → 工具”循环，保留调用预算、降级和会话捕获等保障。（v0.12.1 已修订：E4）
- **对外的一切效果都通过工具产生。** 不调用 `speak` 的正文只算内心独白，只写进日志。
- 工具调用**同步拿到回执**。
- **提交时校验**：每个 Intent 都带 `based_on_seq`。如果在那之后发生了让草稿失效的事件（发言权变化、请求关闭，或剧本标记为 `invalidates_drafts` 的事件），就返回 `STALE`。普通新消息不会让草稿失效。
- 每次 LLM 调用都设置 `max_tokens`（剧本给默认值）。后端仍然使用流式接口，便于超时和取消，但**不广播草稿**。

### 3.3 上下文构建

每次唤醒都重新构建上下文，避免长生命周期的 agent 对话无限增长：（v0.12.1 已修订：E5、E16）

```
system = 角色设定 + 剧本规则正文 (+ 主持人：主持人手册 + 工具说明)
user   = [状态板]   身份/标签 · 公开状态 · 我所在频道及发言权、剩余字数 · 待办请求
                   (主持人：全部频道、队列、请求进度、未结工单、计时器)
         [记忆]     压缩摘要 + 私人笔记
         [可见历史] 上次压缩之后的可见 Ledger 条目（按频道分组，有长度上限）
         [本次唤醒] 唤醒原因 + 新到条目
```

- 同一次唤醒内的多轮调用沿用同一份对话，新到的条目通过注入追加。（v0.12.1 已修订：E5）
- `visible_entries_since(agent, seq)`：只返回 agent **在消息写入时就是成员**的频道条目，以及自己的请求和回执。
- 压缩沿用 `compact_context`。上下文接近窗口上限时，引擎在状态板里提醒 agent 压缩。（v0.12.1 已修订：E6）

## 4. 物理层

### 4.1 频道与发言权

- 频道只能由主持人用 `create_channel` 创建（D12）。
  - 唯一例外（D23）：引擎在开局时为每名玩家自动建一个**系统私聊** `dm-{id}`（成员是该玩家和主持人），作为请求、私密结果和质询的基础设施。主持人可以关闭它，但不能删除。
- 频道的 `mode`：

| 模式 | 谁能写 | 结束方式 |
|---|---|---|
| `closed` | 只有主持人 | — |
| `turn` | 持有发言权令牌的人 | 令牌用尽（条数或字数）、`pass`、到时，或被主持人收回；之后引擎唤醒主持人 |
| `queue` | 队列中当前的持有人 | 每人的令牌用尽、`pass` 或到时后，**引擎自动交给下一个人**；整轮结束后唤醒主持人 |
| `free` | 所有成员（可单独设为只读成员） | **不会自动结束**（D20）。时间或总字数用尽、或者冷场时，引擎只通知主持人；主持人协商后执行 `close_floor` |
| `listen` | 无人可写（主持人除外） | — |

- **发言权令牌** `Floor = {holder, max_messages, max_chars_per_message, max_chars_total, duration_s}`。默认值来自剧本的 `defaults.floor`，主持人可以在单次授予时覆盖。
- **截断（D19）**：超出单条上限或剩余总字数的部分会被截掉，在提交闸门里完成。回执返回 `truncated: {dropped_chars}`；超长的消息在信息流里末尾带 `…`。
- **计时（D14、D18）**：使用固定时长，以单调时钟为准；暂停时冻结剩余时间，恢复后接着走。测试中使用可注入的假时钟。

### 4.2 请求

- `open_request(to, kind, question, options, duration_s, sealed, default)` 立即返回 `request_id`，**不会阻塞**主持人。目标玩家收到 URGENT 唤醒后，用 `respond` 作答。（v0.12.1 已补充：E25）
- 收齐或到时后，引擎关闭请求并唤醒主持人；没有作答的人按 `default` 处理。（v0.12.1 已补充：E25）
- 设置 `sealed: true` 时，关闭之前答案只写在 Ledger 的私有区，关闭时按座位顺序统一公开，以保持盲投的公平性。

### 4.3 模板（D6、D15）

- 剧本声明模板：`{id, text, params, users, sensitive}`。
  - 参数类型有：`player_id`、`player_ids`、`enum`、`int`、`text(max_chars)`。
  - 引擎负责校验类型，并把模板渲染成文本。
- 主持人调用 `announce(channel, template_id, params)`，玩家调用 `speak_template(channel, template_id, params)`。玩家使用模板时**同样受发言权约束**，并且计入字数。
- 敏感模板设置 `users: moderator`。主持人公告的规则写在手册里：敏感信息不得用 `send_message` 自由发送，这一点由提示词约束。
- 模板消息在 Ledger 中带 `template_id` 和 `params`，前端可以据此做结构化展示，例如显示“🗳️ p03 → p05”。（v0.12.1 已修订：E13）

### 4.4 能力

- 剧本声明能力：`{id, holders(表达式), quota, available_when?(表达式), params, on_use}`。
  - `on_use` 只能使用**通用效果**：`freeze_floor(channels)`（冻结队列或发言权）和 `notify_moderator`。
- 玩家调用 `use_ability` 时，引擎依次：校验持有者和配额 → 写入 Ledger → 执行通用效果 → URGENT 唤醒主持人。**具体裁决由主持人完成**，例如白狼王自爆后，由主持人判定出局并公告。

### 4.5 质询（D22）

- 玩家调用 `challenge_moderator(content, ref_seq?)`，内容写入自己的系统私聊并生成 `ticket_id`；主持人收到 URGENT 唤醒。**质询不限次数。**
- 主持人用 `resolve_challenge(ticket_id, verdict: upheld|rejected, reply)` 处理工单。如果判定成立，就通过公告、状态工具或 `reopen_request` 纠正，必要时调用 `hold_game`。
- **惩罚方式**：主持人可以把该玩家的 `dm-{id}` 设为 `closed`，之后该玩家的质询和私聊发言会收到 `CHANNEL_CLOSED`。关闭期间：
  - 主持人仍然可以往这个频道写；
  - 玩家对请求的 `respond` **不受影响**，因为 respond 不是发言；
  - 主持人随时可以重新打开。

### 4.6 硬约束（D10）

- 引擎内置的约束：频道成员资格、发言权、请求是否合法、模板的参数和使用者、能力配额，以及游戏不在运行状态时拒绝一切提交。
- 剧本可以声明额外的约束表达式（违反时返回 `CONSTRAINT`）。`werewolf_12p` **不声明任何额外约束**。

## 6. 生命周期与调度

| 状态 | 进入方式 | 行为 |
|---|---|---|
| `idle` | 新建对局 | 引擎发牌并建立系统私聊 |
| `running` | 开始或继续 | Supervisor 启动 13 个 Actor，以“开始”“继续”或“终局后继续”为原因 URGENT 唤醒主持人；计时器恢复 |
| `paused` | 用户暂停或强制暂停、主持人 `hold_game`、出错（v0.12.1 已补充：E10） | 取消所有 Worker，停止所有 Actor，冻结计时器，存档 |
| `finished` | 主持人 `end_game` | 与 `paused` 相同，另外标记胜者；用户可以点“继续” |

- **Supervisor**：用 `asyncio.TaskGroup` 管理所有任务。Actor 崩溃后从 Ledger 重建；Worker 连续失败时降级为 `wait`，并通知主持人。（v0.12.1 已修订：E3——`wait` 现在是 `sleep`；失败处理的实际行为见 v0.12-contracts.md §3.2、§10.2）
- **LLM 闸门**：全局和每个 Provider 各有一个 Semaphore；每次调用都有 `asyncio.timeout`；每个 agent 有调用预算。（v0.12.1 已修订：E4、E8、E10）
- **看门狗**：如果状态是 `running`，但没有 Worker 在运行、也没有计时器在走，就唤醒主持人“对局静止”；连续 N 次唤醒都没有推进，就自动 `hold_game`。（v0.12.1 已修订：E9）

## 7. 持久化与日志

- **存档**（加密）：Ledger、世界状态（玩家、频道、发言权与剩余时间、队列、请求、工单、变量、随机数状态）、各 agent 的笔记与压缩摘要、用量。`SESSION_SCHEMA_VERSION = 3`，不读取旧版本存档。（v0.12.1 已修订：E20）
- **恢复**：不保存进行中的 LLM 调用。恢复时所有 Worker 都是空闲状态，计时器从冻结的剩余时间继续走，主持人收到“恢复”唤醒。
- **日志**：写在 `<workspace>/.arena/logs/<session_id>/trace-*.jsonl`，明文，单文件约 20MB 后滚动。记录 `llm_call`、`thought`、`tool_call`、`receipt`、`wake`、`cancel`、`inject`、`error`，密钥先脱敏。

## 10. 接口草案（冻结对象）

```python
class Envelope(BaseModel):          # 投递给 Actor
    seq: int                        # 对应的 Ledger seq（纯通知为 0）
    kind: Literal["message", "floor", "request", "receipt", "challenge", "ability", "notice", "timer"]
    priority: Literal["urgent", "normal", "ambient"]   # （v0.12.1 已修订：E1——已去掉 "ambient"）
    channel_id: str | None = None
    sender: str | None = None
    payload: dict[str, Any]

class Intent(BaseModel):            # Worker 的工具调用 -> 提交闸门
    intent_id: str
    actor_id: str
    gen_id: int
    based_on_seq: int
    type: str                       # speak / speak_template / pass / respond / use_ability / challenge / mod.*
    payload: dict[str, Any]

class Receipt(BaseModel):           # 提交闸门 -> Worker（作为工具结果）
    ok: bool
    seq: int | None = None
    code: str | None = None         # NO_FLOOR NOT_MEMBER CHANNEL_CLOSED STALE QUOTA_EXCEEDED INVALID_TARGET
                                    # INVALID_PARAMS REQUEST_CLOSED CONSTRAINT FORBIDDEN GAME_NOT_RUNNING
    message: str = ""
    truncated: dict | None = None   # {"dropped_chars": 120}
    floor_left: dict | None = None  # {"messages": 0, "chars": 0, "seconds": 37}

class LedgerEntry(BaseModel):
    seq: int
    ts: str
```

## 14. 主要风险

| 风险 | 缓解措施 |
|---|---|
| 主持人流程出错 | 在手册里写检查清单；提供 `evaluate`；玩家质询；`hold_game` |
| 上下文过长 | 用状态板加窗口化历史，每次唤醒都重新构建；提醒 agent 压缩（v0.12.1 已修订：E5、E6） |
| 成本暴涨 | 普通消息默认不唤醒；用队列代替逐个调度；主持人对 `free` 讨论只做 AMBIENT 处理；设置预算和并发闸门（v0.12.1 已修订：E1、E5、E6、E8、E10） |
| 自由讨论因主持人迟迟不收尾而拖长 | 时间或字数用尽、或者冷场时，强制 URGENT 唤醒主持人；看门狗 |
| 敏感信息泄露 | 敏感公告强制使用模板；手册约束 |
