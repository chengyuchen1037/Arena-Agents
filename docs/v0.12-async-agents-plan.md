# v0.12.0 开发计划 · 全员异步 Agent 架构（草案）

> 状态：**设计草案 / 待确认**。分支：`dev/v0.12.0`（仅本地，不推送）。
> 基线：v0.11.0（`a6e8c37`）。

## 0. 目标与非目标

**目标**

1. 所有玩家与主持人都改成 **前端 Actor + 后端 Worker** 结构的异步 Agent：
   Actor 随时收消息、随时发消息；Worker 的思考（LLM）和工具执行不会阻塞 Actor 收件。
2. 依然由**主持人维持规则运行**；规则写在剧本里，与引擎解耦（延续 v0.8 起的不变量：引擎不包含任何具体游戏的词汇）。
3. 主持人可以在任意时刻**关闭发言权**；被禁言时引擎拒绝玩家的发言，并返回“无发言权”回执。
4. 可见性**只由频道管理**；任何 Agent（玩家或主持人）都可以在自己有权限的多个频道发言。
5. 玩家可以随时**私聊质询主持人**（例如认为主持人用错了规则），主持人必须处理并回复。
6. 前端：玩家卡片做成极简小块（图案组合 + 短 id + tag），点击 tag 看用量指标；信息流**只显示发言**，**不再流式渲染**。

**非目标（v0.12 不做）**

- 分布式、多进程或多机运行：仍然是单进程 asyncio。
- 真人玩家接入（但协议会为此预留：真人就是一个由 WebSocket 或表单驱动的 Actor）。
- 新增游戏剧本：只迁移 `werewolf_12p`，另加一个最小的测试剧本。

## 1. 现状要点（v0.11）

- 游戏推进由确定性的 `ScenarioDirector` 负责（`app/engine/director.py`），它逐条执行剧本 `workflow` 里的动作。
  `speak` / `choice` / `vote` / `plan` / `interrupt` 都是**同步的请求-响应**：director 先 `await` 一个
  `ParticipantTurn`（`participant_loop.py`，即“流式 LLM → 工具 → 下一轮”），拿到结果再继续往下执行。
- 并发只发生在批处理里（`run_batch`：投票、规划等是 N 人同时回答，结果统一发布）。
  玩家在两个回合之间**没有生命**：不能主动说话，也不能接收消息。
- 主持人在 v0.8 以后就是 director 本身（确定性脚本）。`legacy_moderator.py` 和 `prompts/moderator.md` 只用来兼容 v0.7 存档里的 LLM 主持人。
- 频道是 `Channel{type, status, members, interrupt_quotas}`。可见性按发言时刻的成员快照（`visible_to_ids`）判断，**基础已经具备**。
- 白狼王插话靠**每次发言后私聊轮询一次 yes/no**（`werewolf_12p.md:606-659`）。这正是同步架构的典型代价：
  一天要发十几次 LLM 调用，只为问一句“你要不要插话”。
- SSE 每次都推送**完整会话快照**，流式草稿也通过 `_throttled_stream_broadcast` 推送。前端靠完整快照重绘界面。

## 2. 总体架构

```text
                ┌──────────────────────── Engine (game-agnostic) ────────────────────────┐
                │                                                                         │
 Scenario.md ──►│  Rule Runtime (moderator 的确定性内核)                                  │
                │      │  open/close floor · requests · abilities · eliminate · announce  │
                │      ▼                                                                  │
                │  ┌──────────── Commit Gate (唯一写入口) ────────────┐                   │
                │  │ ACL · floor · phase · quota · 幂等 · 过期校验      │──► Ledger (append-only, seq)
                │  └──────────────────────▲───────────────────────────┘        │           │
                │                         │ Intent                             ▼           │
                │   ┌──────────────── Agent ────────────────┐         Channel Router        │
                │   │ Actor (mailbox, 永不阻塞, 无 LLM)       │◄──── deliver(Envelope) ──┘    │
                │   │   │ wake / inject / cancel              │                              │
                │   │   ▼                                     │        Spectator Projector ──┼──► SSE (增量事件)
                │   │ Worker (LLM 回合 + 工具, 可取消)        │                              │
                │   └─────────────────────────────────────────┘  × 12 玩家 + 1 主持人        │
                │  Supervisor（生命周期 · 重启 · 暂停 · LLM 并发闸门 · 预算）              │
                └─────────────────────────────────────────────────────────────────────────┘
```

### 2.1 核心概念

| 概念 | 职责 | 关键点 |
|---|---|---|
| **Envelope** | 投递给某个 Agent 的一条输入 | `seq, kind(message/request/floor/notice/receipt/challenge), channel_id, from, payload, priority, deadline?` |
| **Intent** | Agent 想对外界产生的效果 | `speak(channel, text)`、`respond(request_id, value)`、`use_ability(name, args)`、`challenge(text)` 等，**一律交给 Commit Gate 校验** |
| **Commit Gate** | 世界状态的唯一写入口 | 同步、无 await 的临界区（单事件循环天然串行），在**提交时**重新校验权限，校验通过才写入 Ledger |
| **Ledger** | 追加式事件日志 | 全局单调递增的 `seq`。它是持久化、断点恢复、SSE 增量推送和上下文构建的**单一事实来源** |
| **Channel Router** | 按频道成员把已提交的事件分发给各 Actor 的邮箱 | 订阅关系由频道成员决定；主持人默认订阅全部频道 |
| **Receipt（回执）** | Commit Gate 对 Intent 的答复 | `accepted(seq)` / `rejected(reason_code, message)`，例如 `NO_FLOOR`（无发言权）、`CHANNEL_CLOSED`、`NOT_MEMBER`、`STALE`、`QUOTA_EXCEEDED` |

### 2.2 Actor（前端）

- 每个 Agent 一个 `asyncio.Task`，主循环是 `await mailbox.get()`。Actor **不调用 LLM，也不做慢 I/O**，所以永远能及时收件。
- 收到 Envelope 后，Actor 先维护本地状态（未读缓冲、待办 request、自己持有的 floor），再按**唤醒策略**决定如何处理 Worker：

| 输入 | Worker 空闲 | Worker 正在运行 |
|---|---|---|
| 发给我的 request（投票、选择、发言邀请） | 立即唤醒 | 下一轮边界注入，并标记为待办 |
| 被授予 floor（轮到我发言） | 立即唤醒 | 注入 |
| floor 被收回 / request 被取消 / 阶段切换导致当前工作作废 | — | **取消**正在执行的 LLM 调用（`task.cancel()`），然后按新状态重新唤醒 |
| 普通频道消息（别人在说话） | 只进入未读缓冲；按防抖规则批量唤醒（可配置，默认不唤醒） | 下一轮边界以“新消息摘要”的形式注入 |
| 自己 Intent 的回执 | 交给 Worker（作为工具结果） | 同左 |

- “注入”的做法：Worker 每完成一轮 LLM 调用后，从 Actor 拿走 `drain_new()` 返回的增量，作为一条 user 消息追加进对话，
  然后再发起下一轮调用。这与 Claude Code / DSH 的 steering 机制相同，不需要中断生成。
- **取消分级**（对应 LangGraph/LangSmith 处理 double-texting 的四种策略 Reject/Enqueue/Interrupt/Rollback）：
  - `URGENT`：直接点名我、主持人提问、floor 被关闭、阶段切换。处理方式是 `cancel` 后重启。
  - `NORMAL`：合并后防抖约 500ms，在边界注入。
  - `AMBIENT`：只进入缓冲区。
  - **防饥饿**：同一个 Worker 连续被取消 2 次后，第 3 次不再取消，改为注入。
  - 每次唤醒都带 `gen_id`，迟到的旧 `gen_id` 结果直接丢弃。
  - 取消后，为还没完成的 tool_call 合成一条“已中断”结果（AgentScope 的做法），保持 tool_call_id 契约完整。
- **正确性靠提交时校验，取消只是省 token 的优化**。即使不取消，迟到的 Intent 也会被 Commit Gate 以 `STALE` 拒绝。

### 2.3 Worker（后端）

- 由现有的 `ParticipantTurn` 演化而来，成为通用的 `AgentWorker.run(trigger)`：多轮“LLM → 工具”循环。保留原有的预算、降级和会话捕获保障。
- **对外效果全部通过工具（Intent）产生**，正文不再自动当作发言：
  - `speak(channel_id, content)`：可以在任何自己有写权限的频道发言，天然支持多频道；
  - `respond(request_id, ...)`：统一替代 `cast_vote` / `answer_yes_or_no` / `submit_choice`；
  - `use_ability(ability_id, args)`：替代“插话”轮询，有配额的玩家可以随时调用；
  - `challenge_moderator(content)`：私聊质询主持人；
  - `pass()` / `end_turn()`；保留共享工具：笔记、文档、上下文压缩。
- 工具调用是同步拿到 Receipt 的：被拒时，Worker 立刻在工具结果里看到
  `{"ok":false,"code":"NO_FLOOR","message":"当前无发言权：主持人已关闭 public 频道发言"}`。
- **提交时校验（commit-time validation）**：LLM 思考期间世界可能已经变化，所以 Intent 在提交那一刻重新校验 floor、阶段和
  request 是否仍然有效，过期的 Intent 一律以 `STALE` 拒绝。这是异步架构正确性的关键。
  - 每个 Intent 都带上 `based_on_seq`，即 Worker 构建上下文时读到的最后一个 seq。
  - 只有当这段时间内发生了剧本标记为 `invalidates_drafts` 的关键事件（出局、阶段切换、floor 变更）时，才判定为 `STALE`。
    普通的新发言**不会**让草稿作废，否则讨论频繁时谁都发不出话。
- **密封提交（sealed request）**：投票这类 request 可以声明 `sealed: true`。在截止或全员提交之前，答案只写入 Ledger 的私有区，
  不对任何人投递；关闭时按座位顺序统一公开。这保留了 v0.11 `run_batch` “盲投”的公平性。
- **发言是工具，不是正文**：v0.11 中“最后一轮的正文就是发言”的做法取消。没有调用 `speak` 的正文一律视为内心独白，不进入任何频道。
- 后端仍然可以使用流式 API（便于超时控制和尽早取消），但**不再广播草稿**，只在提交时产生完整消息。

### 2.4 发言权（Floor）模型：主持人禁言的落地

每个频道有一个 `floor_policy`，由 Rule Runtime 设置：

| 模式 | 含义 | 典型用途 |
|---|---|---|
| `closed` | 任何玩家都不能发言（主持人除外） | 结算、投票期间 |
| `turn` | 只有持有 floor token 的玩家可以发言，token 有次数和期限 | 顺序发言、遗言、警长归票 |
| `free` | 成员都可以发言，可设速率、条数和时间预算 | 狼队夜聊、自由讨论、私聊 |
| `listen` | 成员只能读、不能写 | 观战频道、死亡玩家旁听 |

- floor token：`{holder, channel, max_messages, expires_at_seq / expires_at_time, reason}`。它替代并泛化了现有的 `interrupt_quotas`。
- 主持人可以随时执行 `close_floor(channel)`（例如发现规则错误时冻结频道），玩家此后的 `speak` 会收到 `NO_FLOOR` 回执；
  正在思考的 Worker 会收到“floor 被收回”的信号，根据 2.2 节的策略被取消。
- 每个 Agent 的系统上下文里都会附带一份**当前自己的发言权概览**（在哪些频道可写、还剩几条、截止到什么时候），减少无效尝试。

### 2.5 主持人 = Rule Runtime + Moderator Agent

“主持人维持规则运行”拆成两层：

1. **Rule Runtime（确定性内核，权威）**：从现在的 `ScenarioDirector` 演化而来，按剧本推进流程，
   通过开关 floor、发 request 和等待 request 结果来驱动玩家。它是主持人的“规则手”，不调用 LLM，可以复现、可以测试。
2. **Moderator Agent（LLM，Actor + Worker）**：订阅全部频道和质询队列，负责：
   - **处理质询**：根据剧本规则原文和 Ledger 判断质询是否成立，并私聊回复；
   - **纠错**：确认有错时，在受限的纠错工具集内操作：`announce_correction`、`reopen_request`（重新收集某个选择）、
     `amend_state`（以剧本声明的可修正字段为限）、`hold_game`（暂停并请求人工介入）；
   - **宣布与解说**（可选，可以关闭）；
   - **剧本授权的裁量**：剧本里显式声明的 `judge:` 动作交给它决定。
   - 它**不能**绕过 Commit Gate，不能修改剧本，也看不到 Rule Runtime 之外的“真相”。

> 这个划分的理由：完全依赖 LLM 主持（即 v0.7 的做法）已经被证明不稳定，v0.8 因此改为确定性编排。v0.12 不倒退；
> LLM 主持人只负责“需要判断”的部分（质询、裁量），而且所有操作都必须经过同一个提交闸门。

### 2.6 剧本层（规则与引擎解耦）· schema v2

保持 `schema_version: 1` 的剧本可以继续运行（通过兼容层翻译到新原语），同时新增以下原语：

```yaml
- open_floor: {channel_id: public, mode: turn, holder: "${p.id}", max_messages: 1, timeout_s: 120}
- close_floor: {channel_id: public}
- request:                       # 统一 choice/vote/yes-no/plan；异步发出、等待截止
    to: "${ids(alive())}"
    kind: choice
    question: ...
    options: ...
    deadline_s: 90
    default: none
    save_as: vote
- await_speech: {channel_id: public, from: "${p.id}", timeout_s: 120, save_as: speech}
- free_discussion: {channel_id: wolf-team, members: ..., until: "${...}", max_messages: 12, timeout_s: 180}
abilities:                       # 异步能力：玩家随时 use_ability，引擎校验后触发 handler
  white_wolf_explode:
    holder: "${alive(by_role('white_wolf'))}"
    available_when: "${phase == 'day_speech'}"
    quota: 1
    on_use: [ ...eliminate / announce / goto night_start... ]
```

- 白狼王插话改成 `abilities`：不再在每次发言后轮询，**LLM 调用次数大幅减少**，行为也更接近真实桌游。
- Rule Runtime 处理异步能力时采用“**安全点抢占**”：能力触发后进入队列，Rule Runtime 在下一个动作边界执行
  handler（handler 可以 `goto` 跳转），避免在半个动作中间修改状态。

### 2.7 质询通道

- 每个玩家固定有一个 `dm-{id}` 私聊频道（现在就有），新增 `challenge` 类型的消息，带 `ticket_id`。
- 玩家调用 `challenge_moderator(content, ref_seq?)` 后，Commit Gate 写入 Ledger，并投递给 Moderator Agent（高优先级）。
- 主持人必须回复（`resolve_challenge(ticket_id, verdict: upheld|rejected|needs_human, reply)`），工单状态在前端可见。
- 防滥用：每人每天（每阶段）的质询配额由剧本配置；质询**不会**自动暂停流程，除非主持人认定 `upheld` 并主动执行 `hold_game`。
- 观战端（上帝视角）可以看到全部工单，玩家只能看到自己的工单。

### 2.8 可见性与上下文构建

- 唯一规则：**Agent 只能收到自己发言时刻有权读取的频道的事件**。投递时由 Channel Router 按成员快照过滤，
  构建上下文时再按 Ledger 过滤一次（双保险，并沿用现有的 `visible_to_ids`）。
- Worker 的上下文 = 系统提示 + 剧本公开规则 + 当前私有状态（身份、笔记、floor 概览）+ 可见历史（含压缩摘要）+ 本次唤醒原因。
- 思维链和工具记录**只对自己可见**，不进入任何频道；观战端默认也不展示（见第 4 节）。

### 2.9 LLM 调度与成本

- Supervisor 持有全局和按 Provider 的并发闸门（Semaphore）以及每个 Agent 的 token 预算，触发时降级为 `pass`。
- 普通消息默认**不唤醒** Worker，只积累；只有 request、floor、被 @、私聊、质询回复这几类输入才唤醒。
  这样 13 个 Agent 不会因为每条消息都触发一次调用而导致费用暴涨。
- 每个 Agent 的指标：`llm_calls`、`thinking_rounds`（产生 reasoning 的轮次）、`tool_calls`、`tool_rejections`、
  `prompt_tokens`、`completion_tokens`、`cost_usd`。在现有的 `ActorUsage` 上扩展。

### 2.10 持久化与恢复

- 存档 = Ledger + Rule Runtime 游标 + 各 Agent 的可序列化状态（笔记、压缩摘要、未完成的 request 与 floor）。
- 恢复时**不恢复正在进行的 LLM 调用**：所有 Worker 都置为空闲，未到期的 request 和 floor 会重新投递，Actor 依据 Ledger 重建未读游标。
- `SESSION_SCHEMA_VERSION` 升到 3。v0.11 的存档：**只读回放**，不能在新引擎上继续游玩（待确认，见第 7 节）。

## 3. 前后端协议（SSE v2）

- 不再推送完整快照，改为**带 seq 的增量事件**，并支持 `Last-Event-ID` 断线续传；首次连接和断线过久时发送 `snapshot`。
- 事件类型（初版）：

| 事件 | 载荷 |
|---|---|
| `snapshot` | 投影后的完整状态（不含思维链和工具详情） |
| `message.committed` | `{seq, channel_id, from, content, kind: speech/announce/challenge/reply, ts}`（**完整消息**） |
| `agent.status` | `{id, state: idle/thinking/acting/muted/out, wake_reason?}`（粗粒度） |
| `agent.metrics` | `{id, llm_calls, thinking_rounds, tool_calls, tokens_in, tokens_out, cost}`（节流推送） |
| `floor.changed` | `{channel_id, mode, holders[], expires}` |
| `channel.updated` | `{id, name, type, members, policy}` |
| `phase.changed` / `dashboard.updated` / `game.ended` | 与现有语义相同 |
| `challenge.opened` / `challenge.resolved` | 工单 |
| `request.opened` / `request.closed` | 观战端用于显示“正在投票 7/12” |

- 删除：`StreamingDraft`、`concurrent_streaming_drafts`、`thought_added`、`player_tool_*`、流式节流广播。
- 可选调试接口：`GET /api/agents/{id}/trace`（思维链和工具明细，默认关闭，仅供开发排错，不进入主 UI）。

## 4. 前端改造

1. **玩家小块**（比现在的“紧凑”档还小，约 56×56 到 72×40）：
   - 极简图案组合：外形表示阵营（上帝视角下可见，否则显示中性形状）；填充或描边表示存活/出局；
     角标圆点表示状态（思考中、可发言、被禁言、离线）；
   - 文字只显示 `p01` 和**一个主 tag**（例如“警长”或“出局”）；
   - **点击 tag** 弹出浮层：工具调用次数、思考次数、LLM 调用次数、输入/输出 token、费用、模型名。
2. **信息流**：只渲染 `message.committed`（发言、公告、质询和回复），每条消息到达后整体渲染，不再流式渲染；
   去掉“显示工具调用”“思维链折叠”等控件。
3. **频道栏**：频道列表显示 floor 状态（🔒 禁言 / 🎤 某人持麦 / 💬 自由讨论）和未读数；质询工单单独作为一组，带状态徽标。
4. 布局、主题、工作区、Provider、模板等 v0.11 能力保持不变。
5. 移除 `core.js` 中的快照 diff、流式草稿渲染和思维链渲染代码，引入一个基于 seq 的 store。

## 4.1 参考项目与取舍

完整调研见 [research/async-agent-patterns-report.md](research/async-agent-patterns-report.md)，这里只列取舍：

| 来源 | 借鉴 | 不采纳 |
|---|---|---|
| AutoGen-core | channel 相当于 topic，可见性相当于订阅；区分 direct（request/response）和 broadcast | 不依赖整套 runtime（太重，而且自带模型客户端） |
| LangGraph / LangSmith | double-texting 四种策略，作为取消分级的依据 | 图状态机编程模型 |
| AgentScope | 基于 `CancelledError` 的中断，以及为未完成工具调用合成结果 | MsgHub 自动广播（没有 floor 概念） |
| MetaGPT | 按地址路由到私有缓冲区 | 每轮 gather 形成的回合屏障 |
| OpenAI Agents SDK Realtime | 随时注入输入；在提交边界重新检查条件；取消以 response ID 为作用域 | — |
| Werewolf Arena（Google） | 竞价决定发言权（0-4，4 表示被点名必须回应），可作为 `free` 模式的抢麦策略 | — |
| Time to Talk / LLMafia（EMNLP 2025） | scheduler（等待/发送）与 generator 两阶段；自适应发言率 | 它没有陈旧检查，这正是我们要补上的 |
| Letta sleep-time | 可选：后台整理记忆的 Agent，不在关键路径上 | v0.12 不做 |

依赖：只用 stdlib asyncio（Python 3.11+，需要 TaskGroup 和 `asyncio.timeout`）加 pydantic；不引入 Agent 框架。
