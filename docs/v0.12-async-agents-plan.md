## 0. 决策记录

| # | 决策 |
|---|---|
| D1 | 主持人是**独立 agent**，**不能操控其他 agent 的内部进程**（不能取消、读取或注入别人的 worker）。主持人**不能修改已发生的事**：Ledger 只追加，更正必须写成新条目 |
| D2 | **流程由 LLM 主持人驱动**。轮流发言 = 主持人公告 + 发言权管理，具体方法写在主持人提示词里 |
| D3 | **不兼容旧存档**。删除 legacy moderator、session migration、workflow DSL |
| D4 | 支持观战视角切换：上帝视角，或任意一名玩家的视角 |
| D5 | 思维链和工具明细**只写日志**（明文 JSONL），前端不展示 |
| D6 | 公告采用**混合方案**：敏感公告（出局、投票结果、查验结果、终局）必须用剧本模板发出，其他公告由主持人自由撰写 |
| D7 | **玩家状态可以被改写**（包括复活）。这是主持人通过状态管理工具做的“向前修改”，历史记录本身不变 |
| D8 | **终局由主持人判定**。`end_game` 之后所有 agent 停止；用户在 UI 上点“继续”可以恢复对局 |
| D9 | **由引擎发牌**。主持人另有**随机数工具**；每次抽取都记入 Ledger，可以审计、可以复现 |
| D10 | **硬约束尽量少**。引擎只保证通用的物理规则，游戏规则基本都交给主持人，出错时靠质询纠正 |
| D11 | 日志用**明文**，并限制单个文件的大小 |
| D12 | **频道只能由主持人创建**，玩家不能建频道；主持人默认是所有频道的成员 |
| D13 | `free` 模式的唤醒规则：频道有新消息后防抖约 1.5s 再唤醒，每人有条数上限，玩家可以选择 `wait` |
| D14 | 时限只用**绝对时间**（固定时长），不做排队补偿等复杂计时。另外，因为 token 生成很快，单靠时间上限约束不住发言量，所以**还要限制发言总字数**：单条字数上限，以及每次发言权的总字数上限 |
| D15 | 模板是**通用的结构化消息**：主持人和玩家都可以使用；每个模板声明谁有权使用。例如玩家可以用模板公开表态投票；敏感模板只允许主持人使用。“警长归属”加入模板 |
| D16 | 主持人用什么模型，交给现有的 Provider/模型绑定 UI 管理，不另加提示；剧本模式下，主持人的绑定变为必填 |
| D17 | 开发环境：使用项目现有的 Python 3.12 工具链（与 CI 和 Dockerfile 一致）；本机已有 uv 提供的 3.12.13 |

## 1. 目标与非目标

**目标**
1. 13 个 agent（12 名玩家 + 主持人）都采用 **Actor（前端）+ Worker（后端）** 结构。Actor 随时收件、随时输出，不会被思考或工具执行阻塞。
2. 主持人用工具驱动整个游戏；引擎与具体游戏无关；规则写在剧本里。
3. 发言权由主持人管理。没有发言权时，引擎返回“无发言权”回执。
4. 可见性**只由频道决定**；任何 agent 都可以在自己有写权限的多个频道发言。
5. 玩家可以随时**私聊质询主持人**。
6. 前端：极简玩家块；信息流只显示发言、整条渲染；观战视角可切换。

**非目标**：多进程或分布式；真人玩家（协议上预留）；新增游戏剧本（只迁移 `werewolf_12p`，另加一个测试用的最小剧本）。

## 2. 三层职责

| 层 | 是谁 | 负责 | 不负责 |
|---|---|---|---|
| **引擎（物理层）** | 确定性代码，不含任何游戏词汇 | 频道与成员、发言权、请求（格式、截止时间、密封）、能力配额、提交闸门、Ledger、调度、存档、日志 | 判断谁该说话、谁该出局、是否终局 |
| **剧本** | 一个 Markdown 文件 | 开局配置（身份池、初始频道）、规则文本、主持人操作手册、公告模板、能力声明、检查函数（计票、终局条件，**只是辅助**）、可选的硬约束 | 流程编排 |
| **主持人 agent** | LLM（Actor + Worker） | 读规则、推进流程、管理发言权、发请求、裁决、改玩家状态、公告、处理质询、宣布终局 | 修改历史、操控其他 agent、绕过闸门 |

v0.7 以 LLM 为主持的方案不稳定，这次有三道保险：
1. **引擎物理规则**：主持人想违规也做不到。比如不是频道成员不能发言，没有发言权不能发言。
2. **玩家质询**：主持人用错规则时，玩家可以当场指出，主持人复核后更正。
3. **人工兜底**：主持人可以执行 `hold_game` 暂停对局，等待人工处理。

## 3. Agent 运行时

### 3.1 核心数据

| 概念 | 定义 |
|---|---|
| **Envelope** | 投递给某个 agent 的一条输入。字段：`seq, kind, channel_id?, from, payload, priority`。`kind` 取值：`message`（频道消息）/ `floor`（发言权变化）/ `request`（请求）/ `receipt`（回执）/ `challenge`（质询）/ `notice`（引擎通知）/ `wake`（定时唤醒） |
| **Intent** | agent 想对外产生的效果，由工具调用生成，带上 `based_on_seq` |
| **Receipt** | 提交闸门的回复：`accepted(seq)`，或 `rejected(code, message)` |
| **Ledger** | 只追加的事件日志，每条有全局单调递增的 `seq`。它是存档、上下文、推送和审计的唯一事实来源 |

拒绝码：`NO_FLOOR`（无发言权）、`NOT_MEMBER`（不是频道成员）、`CHANNEL_CLOSED`（频道已关闭）、`STALE`（已过时）、`QUOTA_EXCEEDED`（超出配额）、`INVALID_TARGET`（目标无效）、`REQUEST_CLOSED`（请求已关闭）、`CONSTRAINT`（违反剧本硬约束）、`GAME_NOT_RUNNING`（游戏未在运行）。

### 3.2 Actor（前端，永不阻塞）

- 每个 agent 一个 asyncio 任务，主循环是 `await mailbox.get()`。Actor **不调用 LLM，也不做慢 I/O**。
- 职责：维护未读缓冲、待办请求、自己的发言权概览；决定是否唤醒、注入或取消**自己的** Worker（主持人无权干预，见 D1）。
- 唤醒和取消策略：

| 优先级 | 触发 | Worker 空闲时 | Worker 运行中 |
|---|---|---|---|
| URGENT | 拿到发言权；请求点到我；被 @；私聊或质询回复；发言权被收回；我的请求被取消 | 立即唤醒 | 取消后重启（发言权被收回时只取消、不重启） |
| NORMAL | 我所在频道的普通消息（我在 `free` 讨论中） | 防抖约 1.5s 后唤醒 | 下一轮边界注入 |
| AMBIENT | 其他普通消息 | 只缓冲 | 下一轮边界注入 |

  - **防饥饿**：连续被取消 2 次后，下一次改为注入、不再取消。
  - **代际编号**：每次唤醒带一个 `gen_id`，迟到的旧结果直接丢弃。
  - 取消时，为未完成的 tool_call 合成一条“已中断”结果，保证 tool_call_id 成对。
- **注入**：Worker 每完成一轮 LLM 调用，取出 `drain_new()` 里的增量，作为一条 user 消息追加后再继续。

### 3.3 Worker（后端，可取消）

- 由 `ParticipantTurn` 演化成通用的 `AgentWorker.run(wake)`：多轮“LLM 调用 → 工具”循环，保留调用次数预算、失败降级、会话捕获等现有保障。
- **所有对外效果都通过工具（Intent）产生**。没有调用 `speak` 的正文只算内心独白，只写进日志。
- 工具调用**同步拿到回执**。被拒绝时，Worker 立刻在工具结果中看到原因，例如 `{"ok":false,"code":"NO_FLOOR","message":"public 当前由 p05 持麦"}`。
- **提交时校验**：每个 Intent 都带 `based_on_seq`。如果在此之后发生过“使草稿失效”的事件（发言权变化、请求关闭，或剧本标记为 `invalidates_drafts` 的事件），就以 `STALE` 拒绝。普通新消息不会让草稿失效。
- 后端调用 LLM 仍走流式接口（便于超时控制和取消），但**不广播草稿**。

### 3.4 上下文构建（长生命周期 agent 的关键）

agent 会存活整局，不能让对话无限增长。每次唤醒都**重建**上下文：

```
system  = 角色设定 + 剧本规则文本 (+ 主持人：操作手册与工具说明)
user    = [状态板]   我的身份/标签 · 存活与公开标签 · 我所在频道及其发言权状态 · 待办请求 · (主持人：全部请求、工单、队列状态)
          [记忆]     压缩摘要 + 私人笔记
          [可见历史] 上次压缩后的可见 Ledger 条目（按频道分组，限长）
          [本次唤醒] 唤醒原因 + 新到条目
```

- 一次唤醒之内，多轮 LLM 调用沿用同一份对话，新到的消息通过注入追加。
- `visible_records_since(agent, seq)` 增量过滤：只看自己**当时是成员**的频道，以及自己的请求和回执。
- 压缩：沿用 `compact_context`。另外，主持人上下文接近窗口上限时，引擎会提醒它先压缩。

### 3.5 工具集

**玩家**

| 工具 | 说明 |
|---|---|
| `speak(channel_id, content)` | 在有写权限的任意频道发言 |
| `pass(channel_id)` | 放弃本次发言权，用于让发言队列推进 |
| `respond(request_id, choice, reason?)` | 统一回应：投票、选择、是或否 |
| `use_ability(ability_id, target?, content?)` | 发动剧本声明的能力，例如白狼王自爆 |
| `challenge_moderator(content, ref_seq?)` | 私聊质询主持人 |
| `wait()` | 本次唤醒什么都不做 |
| 共享工具 | `read_document`、`list_documents`、`write_note`、`read_notes`、`compact_context` |

**主持人**

| 类别 | 工具 |
|---|---|
| 公告 | `announce(channel_id, template_id, params)`（敏感公告**只能**用这个）；`send_message(channel_id, content)`（自由文本） |
| 发言权 | `open_floor(channel, holders, max_messages, timeout_s)`、`close_floor(channel)`、`set_floor_queue(channel, order, per_holder=1, timeout_s)`、`pause_queue` / `resume_queue` |
| 频道 | `create_channel`、`update_channel`（成员、开关、模式） |
| 请求 | `open_request(to, kind, question, options, deadline_s, sealed, default)`、`cancel_request`、`reopen_request`（重新收集还没结算的请求） |
| 状态 | `update_player(id, add_tags/remove_tags/set_attributes)`（出局、复活、警徽等都用它）、`set_phase`、`update_dashboard` |
| 辅助 | `random(kind: int/choice/shuffle, ...)`（记入 Ledger）；`evaluate(check_id)`（运行剧本检查函数，例如计票、终局条件，结果只作参考）；`get_ledger(filter)` |
| 质询 | `resolve_challenge(ticket_id, verdict: upheld/rejected/needs_human, reply)` |
| 流程 | `hold_game(reason)`（暂停并等待人工处理）、`end_game(winner, summary)` |
| 共享工具 | 同玩家 |

### 3.6 发言权模型

每个频道都有 `mode`：

| 模式 | 含义 |
|---|---|
| `closed` | 只有主持人能写 |
| `turn` | 只有持有发言权令牌的人能写；令牌有条数上限和截止时间 |
| `queue` | 引擎按主持人给出的顺序依次发放令牌。发言、`pass` 或超时后自动交给下一个人，整轮结束后唤醒主持人 |
| `free` | 成员都可以写，可以设置每人条数上限或速率 |
| `listen` | 成员只读 |

- 有了 `set_floor_queue`，一轮 12 人顺序发言只需要主持人调用 1 到 2 次 LLM，不用每换一个人调用一次。
- 白狼王发动能力时，引擎会**冻结队列**并紧急唤醒主持人，由主持人裁决后再 `resume_queue` 或另行安排。
- 引擎**唤醒主持人**的时机：队列跑完、发言权释放或超时、请求收齐或截止、能力被发动、收到质询、玩家拒绝码出现异常的频率、计时器到点。

### 3.7 请求（异步问询）

- `open_request` 立即返回 `request_id`，**不阻塞主持人**。目标玩家收到 URGENT 唤醒，用 `respond` 作答。
- 收齐或截止后，引擎关闭请求，写入 Ledger，并唤醒主持人。超时的人按 `default` 处理。
- `sealed: true`：在关闭前，答案只写进 Ledger 的私有区，谁也看不到；关闭时按座位顺序统一公开。这样延续了 v0.11 的盲投公平。

### 3.8 质询

- 质询走玩家的 `dm-{id}` 频道（玩家与主持人双向），每条质询带一个 `ticket_id`。主持人收到 URGENT 唤醒。
- 主持人必须执行 `resolve_challenge`。如果判定为 `upheld`（质询成立），就用公告更正，或用状态工具、`reopen_request` 纠正，必要时执行 `hold_game`。
- 配额由剧本配置，例如每人每天 2 次。出局玩家也可以质询。质询**不会**自动暂停对局。

### 3.9 硬约束（尽量少）

- 引擎内置、与游戏无关的规则：频道成员资格、发言权、请求合法性、能力配额，以及游戏未运行时拒绝一切提交。
- 剧本**可以**声明少量额外约束（通用表达式，例如 `"'出局' not in actor.tags or channel.type == 'dm'"`）。`werewolf_12p` 默认**不声明**，出局玩家禁言由主持人通过频道成员或模式来管理。

## 4. 生命周期与调度

| 状态 | 进入方式 | 行为 |
|---|---|---|
| `idle` | 新建对局 | 引擎完成发牌和初始频道 |
| `running` | 开始 / 继续 | Supervisor 启动 13 个 Actor，并唤醒主持人：“游戏开始”或“游戏由用户继续” |
| `paused` | 暂停 / 强制暂停 / `hold_game` / 出错 | 取消所有 Worker，停止所有 Actor，存档；计时器冻结 |
| `finished` | 主持人 `end_game` | 与 `paused` 相同，但标记胜者。**用户点“继续”可以回到 `running`**，此时主持人会收到“对局在终局后被继续”的通知 |

- **Supervisor**：用 `asyncio.TaskGroup` 管理所有任务。Actor 崩溃时从 Ledger 重建；Worker 连续失败时降级为 `wait`，并通知主持人。
- **LLM 闸门**：全局和按 Provider 分别设并发上限（Semaphore），每次调用都有 `asyncio.timeout`，每个 agent 有调用次数或 token 预算。
- **防死锁**：每个请求和发言权都必须有截止时间（剧本给默认值）。如果游戏 `running` 却没有任何 Worker 在运行，也没有计时器，引擎会唤醒主持人提示“游戏处于静止状态”。连续 N 次唤醒都没有推进时，自动 `hold_game`。

## 5. 持久化与日志

- **存档**（加密，与 v0.11 一样）：Ledger、世界状态（玩家、频道、发言权、队列、请求、工单、变量）、各 agent 的笔记与压缩摘要、用量。`SESSION_SCHEMA_VERSION = 3`，不读取旧版本存档。
- **恢复**：不保存进行中的 LLM 调用。恢复时所有 Worker 都是空闲状态，未到期的请求和发言权重新投递，主持人收到“恢复”唤醒。
- **日志**（D5、D11）：写在 `<workspace>/.arena/logs/<session_id>/trace-*.jsonl`，明文，单文件上限约 20MB，超过就滚动。每行一条事件：`llm_call`（模型、token、耗时）、`thought`、`tool_call`（参数和结果）、`receipt`、`wake`、`cancel`、`inject`、`error`。密钥经过现有的脱敏逻辑处理。

## 6. 前后端协议（SSE v2）

带 `seq` 的增量事件，支持用 `Last-Event-ID` 续传；首次连接或差距过大时发送 `snapshot`。

| 事件 | 载荷 |
|---|---|
| `snapshot` | 投影后的完整状态（不含思维链和工具明细） |
| `message.committed` | `{seq, channel_id, from, content, kind: speech/announce/challenge/reply/system, visible_to_ids, ts}` |
| `agent.status` | `{id, state: idle/thinking/acting/waiting/stopped}` |
| `agent.metrics` | `{id, llm_calls, thinking_rounds, tool_calls, rejections, tokens_in, tokens_out, cost}`（节流推送） |
| `floor.changed` / `channel.updated` / `player.updated` | 对应的状态 |
| `request.opened` / `request.progress` / `request.closed` | 观战时显示“投票中 7/12” |
| `challenge.opened` / `challenge.resolved` | 工单 |
| `phase.changed` / `dashboard.updated` / `game.status` | 与现在相同 |

删除：流式草稿、`thought_added`、`player_tool_*`、完整会话快照广播。

## 7. 前端

1. **极简玩家块**（约 64×44）：
   - 由座位号确定的几何图形组合作为头像；
   - 描边或填充表示存活、出局；
   - 角标表示状态：思考中、持麦、等待作答、已停止；
   - 文字只有 `p01` 和**一个主 tag**；
   - **点击 tag** 弹出浮层：工具调用次数、思考次数、LLM 调用次数、token 输入/输出、费用、模型。
2. **信息流**：只渲染 `message.committed`，每条到达后整条显示。没有思维链、工具调用和折叠控件。
3. **频道栏**：显示每个频道的发言权状态（🔒 / 🎤 持麦人 / 📋 队列进度 / 💬 自由）和未读数；**质询工单**单独成组。
4. **观战视角**：下拉选择“上帝视角”或某名玩家。玩家视角下只显示 `visible_to_ids` 包含该玩家的消息，以及他应当知道的 tag。在前端过滤即可。
5. 保留 v0.11 的布局、主题、工作区、Provider 和模板功能。

## 9. 测试策略

- **FakeLLM 脚本**：按 agent 预设“唤醒 → 工具调用序列”，可以注入延迟，并控制“在第 k 轮被取消”。
- **内核单元测试**：邮箱优先级与防抖、取消不泄漏任务、`gen_id` 丢弃旧结果、提交闸门的每一种拒绝码、密封请求、队列推进与超时、防死锁看门狗。
- **场景测试**：脚本化主持人加脚本化玩家，跑完一整局狼人杀；测试暂停后恢复、终局后继续、质询成立后的更正流程。
- **可复现**：随机数带种子，计时器用可注入的假时钟。
- 前端测试：重写受影响的冒烟测试（卡片、流式、绑定入口）。
- 每个里程碑都要求离线全量测试通过（需要先准备 Python 3.11+ 环境）。

## 11. 主要风险

| 风险 | 缓解 |
|---|---|
| LLM 主持人流程出错，比如漏掉某个角色的夜间行动 | 剧本手册写清检查清单；`evaluate` 检查函数；玩家质询；`hold_game` |
| 主持人上下文过长 | 状态板加窗口化历史，每次唤醒都重建；压缩提醒 |
| 成本暴涨（13 个常驻 agent） | 普通消息默认不唤醒；用发言队列；预算与并发闸门 |
| 异步带来的不可复现 | Ledger 加随机数种子加假时钟；只有真实 LLM 部分不可复现 |
| 主持人在敏感公告中泄密 | 敏感公告强制走模板（D6）；自由文本的公告规则写进手册 |
