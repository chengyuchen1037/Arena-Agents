## 0. 约定

- Python 3.12，虚拟环境 `.venv`；运行时务必设 `PYTHONUTF8=1`。**没有 pytest-asyncio**：异步测试用 `asyncio.run(...)` 包一层（`tests/v12/runtime/fakes.py` 里的 `async_test`）。
- **时间**：世界里的所有期限（令牌、请求、自由讨论）和 agent 的 `sleep(seconds)` 闹钟都是**游戏秒**（`clock.now()`，暂停时不走，D18）。运行时的看门狗、LLM 重试的退避和取消宽限期用事件循环的真实时间。（v0.12.0：运行时还有 normal 信封的防抖，E1 已删除。）
- **引擎中立**：`app/world`、`app/runtime`、`app/agents` 里的 Python 源码不得出现任何具体游戏词汇，也不得出现固定的参与者 id 字面量（`p01` 式或 `N1` 式，见 §10.1 第 6 条）；`tests/v12/test_neutrality.py` 会扫描。例外：`app/game/`（编排器包，含演示机器人 `app/game/demo.py`）。（v0.12.0 的契约写的是 `app/orchestrator`、`app/demo/`；编排器最终落在 `app/game/`，扫描清单里仍列着不存在的 `app/orchestrator`，被跳过。）v0.11 遗留的 `app/engine/*.py` 由 `tests/test_engine_neutrality.py` 扫描。
- 世界是**单线程同步**的：处理函数里不能 `await`，也不能做阻塞 I/O；LLM 调用是运行时里唯一的等待点。
- 所有用户可见的文字用**中文**；日志与代码注释中英文均可。
- 所有 JSON 载荷里的 id 都是字符串；`moderator` 是主持人的固定 id，`engine` 是引擎（两者都不能当玩家 id）。玩家 id 是 `N1`–`N12`（E13；编号即座位号；v0.12.0：`p01`–`p12`）；给模型看的称呼是 `N3 Carol`（id + 名字，`render.player_label`），工具参数永远用 id。

## 2. 世界（`app/world`）

### 2.1 `World` 的装配（world-chat）

```python
class World(WorldCore):                       # app/world/world.py
    chat: ChatModule                          # app/world/chat.py
    game: GameModule                          # app/world/game.py
    @classmethod
    def new_game(cls, spec, players: list[dict], clock, *, seed: int | None = None) -> "World"
        # players: [{"id","seat","name","persona"}]（seat / name / persona 可省略）；创建玩家、系统私聊、发牌；状态 idle，未运行
        # id 为空、重复或是保留名（moderator / engine）→ ValueError；身份池与人数不符 → ValueError；
        # seed 缺省时随机取一个并存进世界（存档可复现）
    @classmethod
    def load(cls, data: dict, spec, clock) -> "World"        # 还原 dump() 的结果（clock 已 set 到 data["clock_now"]）
        # dump() 的格式号必须是 1；账本 seq 必须连续（否则 ValueError）；存档时在运行的对局还原后是 paused：
        # 提交闸门是关着的，直到编排器 set_running(True, …) 并 redeliver()
    def snapshot(self, *, max_messages: int = 2000) -> dict   # 观战者的上帝视角快照，见 §2.8
    # WorldPort 要求的其余方法：board / memory / write_note / read_notes_text / compact / display_name ...
```

`World` = 内核 `WorldCore`（账本、提交闸门、投递、表达式）+ 两个 `WorldModule`（`chat`、`game`）。模块注册各自的 Intent 处理函数（`handlers()`），并负责自己的计时（`tick()` / `next_deadline()`）、重新投递（`redeliver()`）与 `dump()` / `load()`。`WorldCore.dump()` = `{"format": 1, "clock_now", "state": WorldState, "ledger": […], "modules": {…}}`；`WorldState` 含玩家、频道、请求、工单、能力、看板、阶段、计数器、随机数种子与状态、每个 agent 的记忆、对局状态（`idle` / `running` / `paused` / `finished`）、胜者与总结（账本单独存）。

运行时和 agent 能调用的全部接口是 `WorldPort`（`app/world/port.py`）：`spec`、`clock`、`seq`、`running`、`set_running`、`submit`、`tick`、`next_deadline`、`redeliver`、`set_notifier`、`drain_outbox`、`drain_events`、`entries_visible(agent_id, *, after_seq=0, limit=None)`、`board`、`display_name`、`memory`、`write_note`、`read_notes_text`、`compact`。

`GameModule` 调用 `self.w.chat.freeze_channel(channel_id, reason)`（world-chat 提供，见 §2.4）。

### 2.2 提交闸门（`WorldCore._submit`，已实现）

顺序（`submit()` 永不抛异常：引擎内部的异常变成 `INTERNAL_ERROR` 回执）：

1. 未知的 Intent 类型 → `INVALID_PARAMS`；
2. 对局没有在运行（闸门关着）→ `GAME_NOT_RUNNING`；
3. 未知参与者（既不是 `moderator` 也不是玩家）→ `UNKNOWN_PLAYER`；
4. 主持人 / 玩家操作错配（`mod.*` 只有主持人能用，其余只有玩家能用）→ `FORBIDDEN`；
5. 载荷用 `INTENT_MODELS[type]` 校验 → `INVALID_PARAMS`（消息列出前 4 个问题）；
6. 过时检查（只查 `speak` / `speak_template`）：自 `based_on_seq` 之后出现过类型在 `spec.invalidates_drafts` 里的账本条目 → `STALE`（`data.latest_seq`）；`pass`、`respond`、主持人的操作不查；
7. 剧本约束：`spec.constraints` 里 `applies_to` 含该类型的，逐条求值 `expr`（变量 `actor`、`intent_type`、`channel`），为假 → `CONSTRAINT`（消息取约束的 `message`）；表达式本身出错 → `INTERNAL_ERROR`；
8. 最后分发给处理函数（没有模块处理该类型 → `INTERNAL_ERROR`）。

处理函数返回 `Receipt{ok, seq, code, message, data, truncated, floor_left}`；`Receipt.tool_json()` 是工具结果文本（紧凑 JSON，去掉空值，`data` / `message` 为空时省略）。**处理函数里的拒绝优先于副作用：被拒绝时不得改动任何状态（不写账本、不投递、不发事件、不动计数器）。**

拒绝码（`Code.ALL`）：`NO_FLOOR`、`NOT_MEMBER`、`CHANNEL_CLOSED`、`STALE`、`QUOTA_EXCEEDED`、`INVALID_TARGET`、`INVALID_PARAMS`、`REQUEST_CLOSED`、`UNKNOWN_CHANNEL`、`UNKNOWN_TEMPLATE`、`UNKNOWN_ABILITY`、`UNKNOWN_REQUEST`、`UNKNOWN_TICKET`、`UNKNOWN_PLAYER`、`ABILITY_DISABLED`、`FORBIDDEN`、`CONSTRAINT`、`GAME_NOT_RUNNING`、`ALREADY_EXISTS`、`INTERNAL_ERROR`。（工具层的 `NOT_FINISHED` 不是世界的拒绝码，见 §4.1。）

闸门的开关：`set_running(running, reason)`。`True` → 对局状态 `running`；`False` → `paused`（`idle` 的对局保持 `idle`，`finished` 的保持 `finished`）。状态变化时写 `game.status`（所有人可见，`{status, reason}`）并发 UI 事件 `game.status`。从 `finished` 回到 `running` 就是“继续”（D8）：`reason` 记为 `continued`，胜者与总结清空。

### 2.3 各 Intent 的语义

**发言类（world-chat）**

| Intent | 语义 |
|---|---|
| `speak` | ① 频道不存在 `UNKNOWN_CHANNEL`（`data.channels` 列出可用的频道）；② 不是成员 `NOT_MEMBER`；③ 模式：`closed` / `listen` → `CHANNEL_CLOSED`（`closed`：只有主持人能写；`listen`：只听频道，成员只能读；系统私聊被关闭时消息说明“你与主持人的私聊已被关闭”）；频道被冻结 → `NO_FLOOR`；`turn` / `queue` → 须持有**活跃且未暂停**的令牌，否则 `NO_FLOOR`（`data` 带 `holders` / `current`）；`free` → 成员不在 `readonly`、也在 `writers`（若设置）内，否则 `NO_FLOOR`；每人条数达上限 → `QUOTA_EXCEEDED`。④ **截断（D19）**：单条上限 = `min(令牌的单条上限, 令牌剩余总字数)`（自由讨论：`max_chars_per_message`；系统私聊：`defaults.dm.max_chars_per_message`，不限条数、不需要令牌）；超出部分截掉，回执 `truncated={"dropped_chars","kept_chars"}`；可写字数为 0 → `NO_FLOOR`。（`content` 最长 20000 字，更长或去掉首尾空白后为空 → `INVALID_PARAMS`。）⑤ 写入 `message`（`kind: speech`）；令牌用掉 1 条、记字数；令牌条数或总字数用尽 → 令牌以 `used` 结束。回执带 `floor_left={"messages","chars","seconds"}`（令牌与自由讨论；系统私聊没有）。 |
| `speak_template` | 与 `speak` 同样的频道与发言权检查，再检查模板：不存在 `UNKNOWN_TEMPLATE`；`users` 为 `moderator` 的模板 → `FORBIDDEN`；参数用 `render.validate_params`（未知参数、缺少必填、枚举 / 整数不合法 → `INVALID_PARAMS`；无效的玩家 id → `INVALID_TARGET`；`text` 超过 `max_chars` 被截断）。**模板文本不截断、不受字数上限约束**，但仍消耗 1 条发言额度并计入字数。`message.kind = template`，带 `template_id` / `params`。 |
| `pass` | 频道不存在 `UNKNOWN_CHANNEL`；不是成员 `NOT_MEMBER`；持有活跃令牌（且频道未冻结、发言组未暂停）→ 令牌以 `pass` 结束；`free` 频道 → 空操作的成功回执（自由讨论没有令牌）；否则 `NO_FLOOR`。 |

**主持人的频道与发言权（world-chat）**

| Intent | 语义 |
|---|---|
| `mod.announce` | 模板须存在（`UNKNOWN_TEMPLATE`），且 `users ∈ {moderator, any}`（`players` 专用的模板 → `FORBIDDEN`）；参数同 `speak_template`；渲染；`message.kind = announce`。主持人可在任何自己是成员的频道写（含 `closed`、`listen`、被冻结的频道）。 |
| `mod.send_message` | 自由文本，按 `defaults.moderator.max_chars_per_message`（2000）截断；`kind = speech`。不计任何额度，但在自由讨论里算一次活动（重置冷场计时）。 |
| `mod.create_channel` | `channel_id`（`^[A-Za-z0-9_-]{1,48}$`）已存在 → `ALREADY_EXISTS`；成员须是玩家 id（否则 `UNKNOWN_PLAYER`），主持人自动加入（`type=public` 也不会自动加入全体玩家）；`type` ∈ `public` / `group` / `dm`（默认 `group`）；`mode` ∈ `closed` / `free` / `listen`（默认 `closed`；`turn` / `queue` 只能经 `open_floor` / `set_floor_queue` 进入）；`mode=free` 时用 `defaults.free` 初始化 `FreeState`。写 `channel.created`，成员（玩家）收到 `notice/channel.created`。频道只能由主持人创建（D12）。 |
| `mod.update_channel` | 改名、增减成员、`readonly_members`（整体替换）、`mode`（`closed` / `free` / `listen`）、`limits`（只接受 free 的键，见 §10.1 第 5 条；`free_limits` 是旧别名）。校验（全部通过才改动状态）：**不能移除主持人**、**系统私聊不能增减成员或改 `readonly_members`**（`FORBIDDEN`；可以改 `mode`，但不能设 `limits`：`INVALID_PARAMS`）；未知玩家 `UNKNOWN_PLAYER`；移出非成员、只读成员不是成员 → `NOT_MEMBER`；主持人不能被设为只读 → `FORBIDDEN`；同一个人不能同时加入和移出 → `INVALID_PARAMS`；设 `limits` 要求更新后的频道是 `free`（否则 `INVALID_PARAMS`），且数值是**整场**的绝对上限：`duration_s` 必须大于已进行的时间，`max_chars_total` 必须大于已用字数。生效：传了 `mode` 就清除 `frozen`；离开 `turn` / `queue` 撤销令牌（`floor.revoked`，`reason: mode_changed`）、离开 `free` 结束自由讨论；进入 `free` 时用默认值初始化（`limits` 覆盖）；`limits` 对运行中的自由讨论同时**重新武装所有 advisory 并重新开始冷场计时**；被移出的成员失去令牌（队列顺延）、不再能写。没有任何变化 → 成功但不写账本。写 `channel.updated`（`changes` 里可能有 `mode{from,to}`、`limits`、`unfrozen`、`name`、`added`、`removed`、`readonly`），频道成员（含被移出的）收到 `notice/channel.updated`。 |
| `mod.open_floor` | `limits` 只有一个，可用的键取决于 `mode`（§10.1 第 5 条）。系统私聊不能开放发言权（`INVALID_TARGET`）。`mode=turn`：`holders` 非空（否则 `INVALID_PARAMS`），且全是频道里的玩家（主持人 → `INVALID_TARGET`；未知玩家 `UNKNOWN_PLAYER`；非成员 `NOT_MEMBER`）；每人一个活跃令牌（限额 = `limits` 覆盖 `defaults.floor`；`deadline = now + duration_s`），各自收到 `floor.granted`；替换原有的发言组或自由讨论（旧令牌撤销，`cause: replaced`）；频道 `mode = turn`，清除 `frozen`。`mode=free`：进入自由讨论（`holders` 非空表示只有这些人可写，同样须是频道里的玩家；限额 = `limits` 覆盖 `defaults.free`），**不向任何人投递信封**——成员下次被唤醒时才从账本读到 `floor.opened`，所以主持人随后要发一条消息开场。 |
| `mod.set_floor_queue` | 按 `order` 建队列（成员校验同上；同一个人可以在队列里出现多次，每个位置一个令牌；`limits`（`FloorLimits`）对所有位置相同）：第一个令牌 `active`，其余 `pending`；一次只有一个活跃令牌。令牌结束后自动激活下一个并投递 `floor.granted`。系统私聊不能建队列。 |
| `mod.pause_queue` / `mod.resume_queue` | 暂停：没有进行中的发言组 → `INVALID_TARGET`；已暂停 → 成功的空操作；`group.paused = True`，活跃令牌的剩余时间存入 `remaining`、`deadline = None`；持有人收到 `floor.paused`（打断）；写 `floor.paused`。恢复：`deadline = now + remaining`，持有人再次收到 `floor.granted`，同时清除 `frozen`，写 `floor.resumed`；没有发言组但频道被冻结（自由讨论）→ 只解除冻结；既没有发言组也没冻结 → `INVALID_TARGET`；没有暂停也没冻结 → 成功的空操作。 |
| `mod.close_floor` | 撤销所有令牌（`cause: closed`），或结束自由讨论；频道 `mode = closed`，清除 `frozen`；活跃令牌的持有人（或自由讨论的可写成员）收到 `floor.revoked`（打断）。写 `floor.closed`。频道本来就没有发言权、也没冻结 → 成功的空操作。 |

**令牌的结束（`_end_token(group, token, reason)`）**：状态变 `done`；写 `floor.token_ended`（频道成员可见；`reason`：`used` / `pass` / `timeout` / `revoked`，另有 `messages_used`、`chars_used`，被收回时有 `cause`）；活跃令牌因 `timeout` / `revoked` 结束 → 持有人收到 `floor.revoked`（`interrupt=True`、`direct`）；`queue` → 激活下一个、写 `floor.granted` 并投递给它；当组内全部结束：组 `completed`，频道变为 `closed`、`group = None`，写 `floor.completed`（`results`：每个令牌的持有人、结果、条数、字数），并 **URGENT 唤醒主持人**（`floor.completed`）。超时在 `tick()` 中处理（`reason: timeout`）。整组被收回（被替换、`close_floor`、改 `mode`）时，没轮到的令牌不留条目，只有活跃的持有人收到 `floor.revoked`。

**自由讨论的 advisory（D20）**：`tick()` 里满足以下之一时，各触发一次，URGENT 唤醒主持人（`free.advisory`，载荷 `reason`：`time` / `chars` / `silence`，附统计）：`now - started_gt ≥ duration_s`；`chars_used ≥ max_chars_total`；`now - last_message_gt ≥ silence_s`（没人说过话则从 `started_gt` 起算）。**这些都不会自动关闭频道**；频道被冻结时不触发；新消息会重置 `silence` 标记；`update_channel(limits=…)` 会重新武装全部三个标记。**每人条数上限是硬限制**（`QUOTA_EXCEEDED`）；`max_chars_per_message` 是硬限制（截断）；总字数与时长只是 advisory。主持人自己的消息不计条数和字数，只重置冷场计时。

**系统私聊（D23，world-chat `create_system_dms()`）**：每人一个 `dm-{id}`，`type=dm`、`mode=free`、`system=True`、`owner`，成员为主持人和该玩家；写 `channel.created`（`actor=engine`），不投递任何信封；主持人可以把它的 `mode` 设为 `closed`（惩罚骚扰），但不能删除它、不能增减成员。

### 2.4 `ChatModule.freeze_channel(channel_id, reason)`

置 `channel.frozen = True`（已冻结则不做任何事，返回 `False`）；`queue` / `turn` 的发言组置 `paused`（剩余时间存入 `remaining`）；
所有当时**能在该频道写**的人（活跃令牌的持有人；`free` 的成员：除主持人、只读成员和不在 `writers` 里的人）收到 `floor.frozen`（`interrupt=True`、normal；令牌持有人是 `direct`，自由讨论的成员不是）；写 `floor.frozen`（频道成员可见，`actor=engine`）。
冻结期间的 `speak` 一律 `NO_FLOOR`（“频道已被冻结，等待主持人裁决”），自由讨论的 advisory 暂停。主持人用 `resume_queue`（自由讨论的冻结也用它解除）/ `open_floor` / `set_floor_queue` / `close_floor` / `update_channel(mode=…)` 解除。冻结由能力的 `freeze_channels` 触发（D25）。

### 2.6 投递（Envelope）目录

`Envelope = {seq, kind, priority, interrupt, channel_id, sender, payload}`：`kind` ∈ `message` / `floor` / `request` / `challenge` / `ability` / `notice`，`payload.event` 是子类型（有 `channel_id` 时它同时出现在信封和载荷里），`seq` 是它所指的账本序号（0 = 无）。世界通过 `WorldCore.deliver(target, kind, event, *, priority="normal", channel_id=None, sender=None, seq=0, interrupt=False, direct=False, payload=None, **extra)` 把信封放进 outbox（`payload` 与 `extra` 合并进信封的 `payload`，`event` 总是在里面），Supervisor 的泵再把它交给收件人（`ENGINE_ID` 交给编排器的 `on_engine`）。规则（E1、E23）：

- **每一个**信封都立刻唤醒收件人，没有 ambient，没有防抖（v0.12.0：`urgent` 立即唤醒、`normal` 防抖后唤醒、`ambient` 从不唤醒空闲的 worker）。`priority`（`urgent` / `normal`）现在只是标注：`urgent` 表示期望收件人采取行动；它不改变唤醒的时机，也不重排唤醒原因（运行时按到达顺序处理）。
- `interrupt=True` 表示“与该频道 / 请求有关的在途工作已经作废”，匹配当前运行 focus 的运行会被取消（§3.2）。
- **发出者不会收到自己条目的信封**（`sender` 等于 `target` 时不投递）。
- 已出局的玩家（带 `spec.ui.out_tags` 里任一标签）只收到 `direct` 的信封——直接发给他本人的事件（他的令牌、他的请求、他系统私聊里的消息、关于他本人的状态变化）；广播不再唤醒他，他仍可以用 `entries_visible` 读历史。主持人和 `ENGINE_ID` 永不过滤；复活（去掉出局标签）后恢复正常。

### 3.2 Actor / Worker 规则

**收件与激活（Actor）**

- **一切投递都唤醒（E1）。** `Agent.deliver(env)` 把信封追加到 `pending`（按到达顺序；`priority` 既不改变顺序也不改变时机）。Worker 在休眠就用 `loop.call_soon` 安排**一次**激活——同一次同步泵里投递的所有信封因此合成**一次**激活，其余不等待、没有任何定时器。（v0.12.0：收件箱按 urgent → normal → ambient 处理，normal 在到达后防抖 1.5 秒才唤醒，ambient 只缓冲；E1 全部删除。）`stop()` 之后的 agent 丢弃投递，重新 `activate()` 后继续。
- **激活**（一次“运行”，`gen_id += 1`，`usage.count(…, "activations")`；重试一次失败的运行不算新的激活）：`brain.begin_run(agent)` → 取走全部 `pending` 作为 `reasons` → 若 `ConversationBook` 里没有这个 agent 的对话：`brain.start_message`（FULL）创建，否则 `brain.inject_message`（DELTA）；DELTA 返回 `None`（没有新条目、没有状态变化、没有唤醒原因）时不调用模型，回到休眠 → 把结果作为 user 消息**追加**到对话 → 进入循环。
- **在途合并**：运行中到达的信封留在 `pending`；Worker 在每一轮的边界——一轮 LLM 调用及其工具执行之后——把 `pending` 一次性交给 `brain.inject_message`，合并成**一条** user 消息（连同系统提醒 `conv.notes`）追加，不额外等待，然后继续下一轮。模型这一轮没有工具调用、但 `pending` 非空时，运行也不会结束，而是带着合并的消息继续。

**一次运行（Worker）**

- 循环 `LLM 调用 → 工具`，**没有轮数上限，也没有执行深度**（E4；v0.12.0：`config.max_rounds[kind][execution_depth]`）。每 50 轮只写一条 trace `long_run`；唯一的刹车是用户设的预算（§6）。LLM 调用在途时状态是 `thinking`，执行工具时是 `acting`。
- 一轮的工具调用在**没有任何 `await`** 的一段里执行：assistant 消息和它的**全部**工具结果一起追加到对话，取消因此不会留下不成对的 `tool_call`；`sleep` 在整批工具都执行完之后才结束运行。被取消的、被丢弃（`stale`）的调用**不写进对话**。
- 模型没有工具调用时：先把正文作为 assistant 消息写进对话；若输出因长度被截断（`finish_reason` 为 `length` / `max_tokens`），每次运行提醒一次“请大幅缩短思考，直接调用工具”（`CUT_OFF_NUDGE`）；否则调用 `brain.no_tool_nudge`，每次运行最多 nudge 一次。
- 运行结束的条件：`ToolOutcome.ends_run`（`sleep`）；或模型没有工具调用，`no_tool_nudge` 返回 `None` 或已 nudge 过，且没有待合并的信封（等同不定时 `sleep`，trace `run_end` 的 `reason` 为 `no_tool`）；或激活没有可说的内容（`nothing`）；或被取消、被丢弃。结束时如果 `pending` 又非空，立刻再激活一次。
- `ToolOutcome.rebuild=True`（`compact_context`）：丢弃对话，`brain.reset_conversation(agent)`，用 `start_message` 重建一条新对话并继续（见“压缩”）。
- 每次运行 `gen_id += 1`，`gen_id` 随 Intent 带给世界（诊断用）。运行一旦失效（被取消、被停止、被新的运行取代），LLM 调用返回之后立即丢弃结果，**不再执行任何工具、不再向世界提交任何 Intent**。

**持久会话（E5）**

- **对话是持久的、只追加的**：每个 agent 一份 `Conversation{system, tools, tools_sig, messages, seen_seq, sleep_until, slept_s, last_input_tokens, epoch, …}`，每次调用发送 `[system] + conversation.messages`。`system` 与 `tools` 在对话创建时确定并保持不变（逐字节相同，供应商的前缀缓存才能命中）；之后只追加：开场的 FULL 消息、每次激活的 DELTA、assistant 消息及其工具结果、在途合并的消息。只有两种操作会改写前缀，都罕见且计入 `epoch`：重建（`compact_context`）和兜底裁剪。（v0.12.0：每次运行都用 `brain.start_message` 重建上下文，对话不跨运行保留。）
- `seen_seq` 是最近一次 FULL / DELTA 消息构建时的世界序号（`brain` 返回），随后的工具调用用它作为 Intent 的 `based_on_seq`（§2.2 的过时检查）。
- **`ConversationBook`**（由编排器持有，每局一个）：`get(agent_id)`、`put`、`reset(agent_id=None)`、`agents()`；存档不保存对话（不需要 `dump()` / `load()`）。构造 `Supervisor(…, book=…)` / `Agent(…, book=…)`。编排器在暂停 → 继续时复用同一个 book（对话和 `sleep_until` 因此保留），`Brain` 实例也跨暂停复用（系统提示词逐字节不变）；新局、洗牌身份、导入、从存档恢复时丢弃并重建 book 和 `Brain`（对话从账本重建一次，每个 agent 一次缓存未命中）。

**打断（E7）**

- 运行中收到 `interrupt=True` 的信封，且其 `channel_id` 或 `payload.request_id` 与当前运行的 **focus** 匹配 → 取消该运行（`task.cancel()`；这次 LLM 调用的结果丢弃、不写进对话），并带着全部 `pending`（打断它的信封在内）立刻重新激活（DELTA）。**focus** = 本次运行消费过的所有信封里出现的 `channel_id` 和 `request_id`（v0.12.0：只算 urgent / normal 的信封）。既没有 `channel_id` 也没有 `request_id` 的打断匹配不到任何 focus，只是合并。新的运行等被取消的 Worker 收尾之后才开始；超过 `cancel_grace_s`（5 秒）还没收尾就放弃它，它迟到的结果被丢弃。
- **防饥饿**：同一个 agent 连续被取消 `starvation_limit`（2）次后，第 3 次打断不再取消，改为在下一个轮边界合并。一次运行正常结束后计数清零；没有调用过模型的空激活不清零。

**休眠与定时器（E3）**

- `ToolOutcome.sleep_s`（只在 `ends_run` 时有效；一批里有几个 `sleep` 取最短的有效值，不是正数则没有定时器）→ 运行结束时 `Conversation.sleep_until = clock.now() + sleep_s`（**游戏时钟**，暂停时冻结；`slept_s` 记下请求的秒数）；运行结束时 `pending` 非空则不设（立刻再激活）。
- Supervisor 的 tick 轮询每个 agent 的 `timer_due(now)`（没有运行、没有待处理的信封、没有已安排的激活或重试，并且 `now >= sleep_until`），到点合成 `Envelope(kind="notice", priority="normal", sender=ENGINE_ID, payload={"event":"timer.elapsed","slept_s":…})` 激活它。休眠期间有任何信封到达，定时器作废（激活开始时清除）；但若那次激活没有可说的内容（DELTA 为 `None`），闹钟原样恢复。
- 暂停 → 继续：对话和 `sleep_until` 都留在 `ConversationBook` 里，游戏时钟冻结，所以闹钟接着走。

**状态（E2）**

- 只有三种：`thinking`（LLM 调用在途）、`acting`（执行工具，或两轮之间）、`sleeping`（没有运行：等下一个信封，或等自己设的闹钟；对局暂停 / 结束时也是 `sleeping`）。事件 `agent.status`：`{"id","state","until"}`，`until` 只在 `sleeping` 且有闹钟时是闹钟的结束时刻（游戏时钟秒），否则为 `null`；状态或 `until` 变化时才发。（v0.12.0：`idle` / `thinking` / `acting` / `stopped`。）

**压缩（E6）**

- 每次 LLM 响应后 `used = prompt_tokens + cache_read_tokens + cache_write_tokens`（这次调用的输入总量）；`window = context_window()`（该 agent 的模型绑定的 `context_window_tokens`；未知或 ≤ 0 时既不提醒也不裁剪）。
- `used >= compact_at * window`（默认 0.6）且本对话尚未提醒过 → 在下一条 user 消息里附上系统提醒（`COMPACT_NUDGE`：“会话已接近上限，请先调用 compact_context 生成摘要，再继续”）；agent 调用 `compact_context` → `ToolOutcome.rebuild=True` → 丢弃对话，用 `start_message` 重建（`system` 与 `tools` 逐字节不变，`epoch + 1`，唤醒原因 = 本次运行消费过的信封）。由 `compact_context` 重建出的对话，只有在输入比刚重建时又增长了 `MIN_COMPACT_GAIN * window`（10%）之后才会再次提醒——开局信息本身就超过阈值时（小窗口模型）重建释放不了任何空间，不应该“压缩—重建—再压缩”地循环。
- `used >= trim_at * window`（默认 0.9）仍未压缩 → 兜底裁剪：从对话最前面起，按**完整的轮**（开场的 user 消息、assistant 消息及其全部工具结果）删除，直到估计低于 `compact_at`；开局的 FULL 消息和最新的一轮永远保留；裁剪后在下一条 user 消息里告知（`TRIM_NOTICE`）；trace 事件 `trim`（裁不动时 `trim_failed`）。

**失败与重试**

- LLM 调用失败（异常、超时）或 Brain 出错：记录 trace `error`，指数退避后重试**同一次运行**（`llm_retries`=2 次重试，即最多 3 次尝试；退避 `retry_backoff_s`=1 秒起、每次翻倍、上限 `retry_backoff_max_s`=30 秒）。重试时对话保持原样，退避期间到达的信封并入重试；仍失败则放弃本次激活（trace `give_up`），通过 `sink` 发出 `error` 事件，agent 回到休眠；不得拖垮其他 agent。

**并发闸门（E8）**

- `llm_concurrency` / `llm_concurrency_per_provider` 为 `0` 表示不限（默认）；闸门只为应对 Provider 的速率限制（429 由 LLM 客户端退避重试），不是省钱手段。LLM 超时 `llm_timeout_seconds` 保留（可靠性）。

**不变量**（`tests/v12/runtime/test_agent_fuzz.py`）：同一个 agent 任何时刻最多一个在途的模型调用；被取消的运行此后不再行动，每个工具调用都属于一个已启动的运行；每个请求里的 `tool_call` 都有成对的结果，并且在同一个 `epoch` 内逐字节延伸上一次请求；每次激活都有交代（结束、被取消或失败）；每个已投递的信封都被告知给了模型（是某次开场 / 增量的一部分）；结束后没有残留的任务和待处理的信封，agent 处于休眠；取消、停止后不得泄漏任务。

### 3.3 Supervisor 规则

- `start(initial_wakes)`（同步，须在运行中的事件循环里调用）：登记世界的通知器；对每个 agent `activate()`（易失状态清零，对话与闹钟保留，发布 `sleeping`）；对 `initial_wakes: dict[agent_id, list[Envelope]]` 投递（未知 id 忽略）；调用 `world.redeliver()` 后立即泵一次；启动三个后台任务：tick 轮询、看门狗、metrics 发布。
- 泵：`world.drain_outbox()` → 按 `target` 交给 `Agent.deliver`（`ENGINE_ID` → 调用 `on_engine(envelope)`）；`world.drain_events()` → `sink.publish`。由世界的通知器经 `loop.call_soon` 触发，去重：同一轮事件循环里任意多次变化只泵一次，一次泵里给同一个 agent 的信封合成一次激活。
- tick 轮询（每 `tick_interval`；`SupervisorConfig` 默认 0.25 秒，`config.yml` 取 0.1 秒）：`world.tick()`（令牌、请求、自由讨论的计时；暂停时是空操作）→ 泵 → `poll_timers()`（唤醒 `sleep(seconds)` 到点的 agent；放在泵之后，所以刚被世界唤醒的 agent 的闹钟已经作废）。`world.tick()` 抛异常只记日志、发一次 `error` 事件，不停止轮询。
- `stop()`：先让每个 agent 同步停止（取消 worker 和已安排的激活，清空 `pending`，发布 `sleeping`），取消三个后台任务，有限地等它们和被取消的 worker 结束（顽固的放弃），发最后一次 `agent.metrics`，再泵一次（给 agent 的投递丢弃，但 ENGINE 通知和世界事件照常发出）。**不得泄漏任务**（测试里要检查）。停止后世界的通知器仍然登记着。
- **看门狗**（真实时间；`watchdog_s`（默认 20 秒）、`max_watchdog_wakes`（默认 3）、`watchdog_poll_s` 可注入）：`running` 时，如果所有 agent 都静止（`Agent.is_quiet()`：没有运行、没有待处理、没有已安排的激活或重试）、主持人没有定时休眠（那是它自己的计划；玩家的闹钟不算）、`world.next_deadline() is None`，并且这种静止持续满 `watchdog_s`（其间账本 `seq` 没有任何变化）→ 向**主持人（只向主持人）**投递 urgent `notice/watchdog`（`idle_s, attempt, max_attempts, seq`）。连续 `max_watchdog_wakes` 次唤醒仍没有让 `seq` 前进后，再静止一个 `watchdog_s` 时调用一次 `on_stall(reason)`（`reason` 是一句中文说明；编排器据此在界面上显示警告横幅 `stall_notice`），并照常再唤醒一次主持人，此后继续每隔 `watchdog_s` 唤醒。任何 `seq` 前进都会清零计数；若之前报过警，则调用 `on_stall(None)` 撤下横幅。**看门狗从不暂停对局**（E9；v0.12.0：`on_stall` 里编排器 `hold_game`）。暂停期间不计时。
- 状态事件：agent 自己发 `agent.status`（§3.2）；Supervisor 每 `metrics_interval_s`（默认 1 秒）对**数字有变化**的 agent 发 `agent.metrics`（还没有任何记录的不发），停止时再发一次。编排器对不属于对局的 actor（赛后复盘时玩家的一次性调用、“完善”用的伪 actor `roster`）在记账时直接补发 `agent.metrics`，让界面上的合计与服务端一致。

### 3.4 LLM 调用与记账

- 每个 Worker 的 LLM 调用：`resp = await llm.complete(agent_id, conv.request_messages(), conv.tools, max_tokens=…)`；`max_tokens = AgentConfig.max_tokens`（默认未设），否则 `spec.defaults.llm.max_tokens`（默认 8192；推理模型的思考也算进去）。回答不会流式推给界面（D5）。
- 成功后：`usage.record_llm(agent_id, resp)`（四类 token 与价格快照；随后同步调用 `UsageBook.on_record`，编排器在里面检查预算）；`conv.last_input_tokens = prompt + cache_read + cache_write`；有 `resp.thought.strip()` → `count(..., "thinking_rounds")`；每个工具调用 `count(..., "tool_calls")`；回执 `ok=False` → `count(..., "rejections")`；每次激活 `count(..., "activations")`。
- trace 事件（只写日志，从不发给界面，D5、D11）：Agent：`wake`、`conversation`、`inject`（`kind`：`activation` / `merge`）、`llm_call`（模型、四类 token、`finish_reason`、工具名、耗时；`trace_messages` 打开时还带完整对话）、`thought`、`content`、`tool_call`（参数与结果）、`receipt`、`run_end`、`sleep`、`timer`、`cancel`、`inject_instead_of_cancel`、`discard`、`nudge`、`compact_nudge`、`rebuild`、`trim`、`trim_failed`、`retry`、`give_up`、`long_run`、`error`；Supervisor：`watchdog`（`action`：`wake` / `stall` / `recovered`）。

## 4. 智能体层（`app/agents`，agents）

`Brain`（见 `app/runtime/ports.py`）的实现 `ArenaBrain(world, spec, cfg, *, docs_dir=None, personas=None, memories=None, history_chars=None)`：`personas` / `memories` 是座位 id → 性格 / 长期记忆文本（开局时的名册快照），`history_chars` 覆盖可见历史的字数预算。（v0.12.0：`ArenaBrain(..., execution_depth=…)`，E4 删除。）`Brain` 协议：`system_prompt`、`tool_schemas`、`begin_run`、`reset_conversation`、`start_message`（FULL）、`inject_message`（DELTA）、`no_tool_nudge`、`execute_tool`；输入 `WakeContext{agent_id, kind（start / inject）, gen_id, reasons, after_seq}`，工具结果 `ToolOutcome{text, receipt, ends_run, sleep_s, rebuild, shared}`。

### 4.1 工具

工具名 = Intent 类型去掉 `mod.` 前缀；唯一例外：玩家的 `challenge` 工具名为 **`challenge_moderator`**。工具参数 = 对应载荷模型的字段（`model_json_schema()` 清洗后：展开 `$defs`、去掉 `title`、把 `anyOf [x, null]` 压成 `x`，并补上字段说明）。

| 角色 | 工具 |
|---|---|
| 玩家 | `speak`、`speak_template`（仅当剧本有玩家可用的模板）、`pass`、`respond`、`use_ability`（仅当剧本有能力）、`challenge_moderator`、`sleep`、共享工具 |
| 主持人 | `announce`、`send_message`、`create_channel`、`update_channel`、`open_floor`、`set_floor_queue`、`pause_queue`、`resume_queue`、`close_floor`、`open_request`、`cancel_request`、`reopen_request`、`update_player`、`set_phase`、`update_dashboard`、`random`、`evaluate`、`get_ledger`、`resolve_challenge`、`hold_game`、`end_game`、`enable_ability`、`disable_ability`、`sleep`、共享工具 |
| 共享 | `list_documents`、`read_document`、`write_note`、`read_notes`、`compact_context` |

- 世界类工具：`Intent(actor_id, gen_id, based_on_seq=seen_seq, type, payload)` → `world.submit` → `ToolOutcome(text=receipt.tool_json(), receipt=receipt)`。参数 JSON 解析失败 → 运行时直接把错误作为工具结果交还给模型（`{"ok":false,"error":…}`），不会到达 brain 和世界（`app.engine.toolargs`）；参数不是 JSON 对象、或工具名未知 → `INVALID_PARAMS` 回执。
- **`sleep(seconds?)`（E3，取代 `wait`）**：`ends_run=True`；`seconds` 是游戏时钟秒，1–3600（范围外的数值被夹到范围内；不是数字或不是有限数 → `INVALID_PARAMS`），不带 = 睡到有新信封为止。（v0.12.0：`wait`，不带参数。`wait` 现在只是不公布的别名，仍可执行，等同不带参数的 `sleep`。）软护栏：玩家第一次 `sleep` 时若还有未作答的请求（剩余 > 2 秒）或仍持有发言权（还有可发条数、未暂停 / 冻结），先返回 `{"ok":false,"code":"NOT_FINISHED",…}` 并**不**结束运行，提醒他处理；每项事务每次运行只提醒一次，再调用一次 `sleep` 就真的休眠。主持人没有这类事务（等答案是它的本职）。
- `compact_context(summary_markdown, keep_recent_count?)`：`keep_recent_count` 默认 10，夹到 4–25；调用 `world.compact`（`summary_upto_seq` 前移，只前进不后退），`rebuild=True`。
- `write_note(title, content, mode)`：标题 ≤ 60 字，正文 ≤ 4000 字（超出被截断，`truncated: true`），`mode` 为 `overwrite`（默认）/ `append`；`read_notes`。笔记只有本人可见，随存档保存。
- `list_documents` / `read_document(doc_name)`：读 `config.yml` 的 `knowledge_base.docs_dir`，只允许 `.md` 文件的裸文件名（禁止路径穿越），单篇 ≤ 60000 字；文件名以 `moderator_` 开头的文档只有主持人看得到、读得到。（实现在 `app/agents/docs.py`。）
- 每个 agent 最近的行动（最多 12 条，不持久化）由 brain 记录：除 `sleep` 外的每次工具调用都记一条 `名称(参数) → 结果`（成功、被拒绝及原因码、被截断），下次开新对话（FULL 消息）时展示给本人。

### 4.2 上下文格式

**FULL 消息（`start_message`，对话的第一条 user 消息）**，固定段落（中文小标题）：`【状态板】`（`board()` 渲染）→ `【我的记忆】`（压缩摘要 + 笔记）→ `【我最近的行动】` → `【可见历史】`（`entries_visible(after_seq=summary_upto_seq)`，按时间顺序，每行 `#seq [频道] 名字：内容`，系统类条目用一行摘要；总长度有上限：玩家约 12k 字，主持人约 20k 字，超出时丢弃最旧的，并在状态板顶部提示“可见历史较长……请把关键信息写进笔记，必要时调用 compact_context”）→ `【本次唤醒】`（新消息按频道合并成一行，其余每个 `reasons` 信封一行，最多 14 行）。返回的 `seen_seq` 是构建时的世界序号。它同时记下这块状态板，作为之后增量的基线。

**DELTA 消息（`inject_message`）**：`【游戏时间】` + `【新动态】`（`ctx.after_seq` 之后新增的可见条目，字数预算约 8k）+ `【状态变化】`（只写与上一条消息相比**可行动**的变化：对局状态；玩家本人的标签 / 属性 / 身份说明；频道的新增、改名、模式、冻结、成员、只读成员、我能不能写与发言权的变化、离开的频道；请求的新增 / 作答 / 结束与共享答案；能力的启用与次数；工单；主持人另有对局面板。不写时钟和不断变化的计数，也不写阶段文字——阶段由 `phase.changed` 条目出现在【新动态】里）+（玩家）“你当前可以发言的频道”+ `【本次唤醒】`。什么都没有（没有新条目、没有变化、没有唤醒原因）时返回 `None`，运行不调用模型。brain 没有这个对话的基线时（如恢复后的对话）先整块刷新一次状态板。`ctx.after_seq` 是该对话已经被告知的最后一个账本序号。

玩家写的内容（发言、答案、理由、质询预览）嵌进别人的上下文前都经过 `sanitize.neutralize_untrusted_text`：续行加缩进标记、伪造的段落标题 / 角色前缀 / 分隔标签被拆掉，保证玩家的话只是数据，不会伪造一条记录或一个章节。

### 4.3 系统提示词

玩家：`prompts/participant.md` 的模板 + 剧本 `rules_text`；主持人：`prompts/moderator.md` + 剧本 `rules_text` + `manual_text`（路径可由 `config.yml` 的 `prompts.*` 改；文件缺失时用内置的兜底文本）。模板变量：`{{id}}`（`N3`）、`{{name}}`（`Carol`）、`{{seat}}`（`3`）、`{{persona}}`（性格设定；为空时是“（没有特别设定，按你自己的判断行事。）”）、`{{memory_block}}`（含小标题“# 你的记忆与经验”的整段，只给玩家；记忆为空或“本局不加载记忆”时为空串）、`{{memory}}`、`{{rules}}`、`{{manual}}`。系统提示词和工具 schema 每个 agent 只构建一次并缓存（逐字节稳定，前缀缓存才能命中）。工具使用要点由提示词文件承担，不写在代码里。
`no_tool_nudge`：每次运行最多一次。本次回答有正文但没有任何工具调用，或玩家还有未处理的事务（未答的请求 / 仍占着的发言权）时返回提示（“你的正文不会发送到任何频道；要发言请调用 speak（或 speak_template），如果现在不需要做任何事，请调用 sleep 进入休眠”，另附未处理的事务）；没有正文也没有未处理的事务时返回 `None`，运行安静地结束。（v0.12.0：提示里是 `wait`。）

| 键 | 默认 | 含义 |

### 8.2 SSE v2 事件

传输：`GET /api/events`，`text/event-stream`。每条消息 `id: <event_id>` 加 `data: {"id":N,"type":"...","data":{...}}`（**不带 `event:` 字段**，前端用 `onmessage`）。第一条是 `snapshot`。

### 10.3 LLM 用量、价格、价格源（lead）

- `LLMResponse`：`prompt_tokens` 改为**未命中缓存的输入**；新增 `cache_read_tokens`、`cache_write_tokens`；价格快照新增 `cache_read_price_per_m`、`cache_write_price_per_m`（已按“空 → 输入价”解析成数字）。`cost = (prompt·in + cache_read·cr + cache_write·cw + completion·out) / 10⁶`。
- `UsageBook`：`by_model`、`by_actor` 和总量都含 `calls, prompt_tokens, cache_read_tokens, cache_write_tokens, completion_tokens`；费用在 `by_model` / `by_actor` 里是 `cost_usd`，总量里是 `total_cost_usd`；`by_actor` 另有 `activations, tool_calls, thinking_rounds, rejections`；`total_tokens` = 四类之和；`cache_hit_rate = cache_read / (prompt + cache_read + cache_write)`（总量、每个模型、每个 agent 都有）。`by_model` 的键是 `"<provider_id>::<model_id>"`，值里还有最近一次调用的四个价格。没有价格快照的调用按 `UsageBook` 自带的兜底价格计费。
- `ModelEntry`（`app/providers/models.py`）：`id, input_price_per_m, output_price_per_m, cache_read_price_per_m: float|None, cache_write_price_per_m: float|None, context_window_tokens, price_source: str`（`"manual"` 或 `"litellm:<key>"`）。旧数据迁移：新字段为空、`price_source="manual"`。
- 价格源：`GET /api/pricing/source` → `{"url","default_url","fetched_at","entries":n,"error":null|str}`；`PUT /api/pricing/source` `{"url"}`（空串 = 默认源）；`POST /api/pricing/refresh`（下载失败不是 HTTP 错误：旧表保留，`error` 字段说明原因）；`GET /api/pricing/match?provider_id=&model_id=` → 匹配到：`{"matched":true,"key":str,"input_price_per_m","output_price_per_m","cache_read_price_per_m","cache_write_price_per_m","context_window_tokens","price_source"}`；没匹配到：`{"matched":false,"key":null}`。`POST /api/providers/{id}/discover-models` 的响应是 `{"models":[…],"existing_models":[…],"suggested":{"<model_id>": 同上字段或 null}}`（`suggested` 是以模型 id 为键的对象）。

### 10.9 主持人的随机头像（rev3，用户要求：“主持人头像也要用随机生成的头像”）

主持人**不是座位**，但和玩家一样有一个由头像素材库随机组合的像素头像（旧的固定“礼帽”图标只在后端没有给出头像、或素材库缺失时作为回退）。

- **名册**：`<数据目录>/roster/roster.json` 里多一个 `moderator: {"avatar": {…}}`（没有名字、性格、记忆可设；名字固定“主持人”）。`GET /api/roster` 多一个 `moderator: {"id":"moderator","name":"主持人","avatar":{…}|null}`；座位列表仍是 12 个。名册第一次建立时，12 个座位和主持人**一起挑选**（13 个头像两两至少 3 项素材不同）；旧名册（没有主持人头像）在第一次读取时只补主持人的头像，玩家头像保持不变。
- **本局快照**：`GameSession.moderator_avatar`（存档 v4 的一个字段），开局创建时从名册复制，本局内不变。
- **API**：`PUT /api/roster/moderator {"avatar": {…}}`（只允许 `avatar`；带 `name` / `persona` / `memory` → 400“主持人只能更换头像…”）；`POST /api/roster/moderator/avatar:regenerate` → `{"id":"moderator","name":"主持人","avatar":{…}}`，新头像与全部玩家头像明显不同；`POST /api/roster/avatars:regenerate` → `{"seats":[…],"moderator":{…}}`（“重新生成全部”包含主持人）。`POST /api/roster/moderator/refine` → 400（主持人没有性格设定和记忆）。和玩家一样只能在对局未开始时修改（409）。
- **PublicSession**：`session.moderator` 多一个 `avatar`（描述对象或 `null`）。
- **SSE**：`roster.updated` 的数据多一个可选的 `moderator: {"id":"moderator","avatar":{…}}`（主持人不是参与者，所以不在 `participants` 里）。后端每次都带全部座位的 `{id,name,avatar}`（只改主持人时也是）；前端容忍 `participants: []`（模拟服务只改主持人时就这么发）。
- **前端**：`Avatar.urlFor("moderator", …, desc)`——有素材库且有合法描述时按描述渲染，否则回退到固定礼帽；信息流里主持人的消息、顶栏的主持人芯片、主持人详情面板都用这张头像；主持人详情面板在对局未开始时有“🎲 重新生成头像”。

### 11.2 数据目录（storage 提供）

### 11.6 存储细节（storage 补全）

> 代码是权威；用户向的说明见 [storage.md](storage.md)。以下是跨流需要依赖的确切行为。

**数据目录与进程锁**

- `get_data_dir()` / `ensure_data_dir()` 见 §11.2。补充：`ensure_data_dir()` 同进程幂等；换目录（测试里改 `ARENA_DATA_DIR`）时先锁新目录、再放旧目录，失败则保持旧锁；被占用抛 `app.storage.datadir.DataDirLockedError`（`StorageError` 的子类，消息同 §11.2；只在锁冲突的错误码 EACCES / EAGAIN / EWOULDBLOCK 时抛——文件系统根本不支持锁（部分网络盘 / 绑定挂载）时只记一条警告、照常启动）；目录建不了抛普通 `StorageError`。另有 `release_data_dir()`（干净退出 / 测试，`reset_stores_for_tests()` 会调）与 `held_data_dir()`。
- 启动语义：`main.lifespan` 最先 `ensure_data_dir()`——`DataDirLockedError` **向上抛，拒绝启动**；其它 `StorageError` → `app.state.degraded = True`，服务照常起来（存储相关接口 503）。`orchestrator.startup()` 返回 `{"restored": <session_id>|None, "recovery_error": str|None}`：先 `ensure_data_dir()`（被占用同样向上抛；目录不可用 → 返回 `recovery_error`、不开自动保存）→ 重读配置 → 恢复上次对局（暂停）→ 开自动保存。没有 `workspace` / `migration` 字段了。
- 数据目录里不属于“数据”的运行时文件只有 `.lock` 和 Windows 的 `master.v1.dpapi`（导入的备份 / 回滚要把它们排除在“整体搬走”之外）；`tmp/`、`backups/`、`exports/` 由 archive 管。
- 已删除的环境变量（代码不再读取）：`ARENA_WORKSPACE_DIR`、`ARENA_DISABLE_WORKSPACE`、`ARENA_DISABLE_LEGACY_MIGRATION`、`ARENA_MAX_IMPORT_BYTES`。保留：`ARENA_DATA_DIR`、`ARENA_DEMO`、`ARENA_MASTER_KEY(_FILE)`、`DEEPSEEK_*`。

**文件格式**

| 文件 | 格式 |
|---|---|
| `settings.json` | 明文 JSON，schema 2 不变（`default_bindings`、`last_session_id`、`ui`、`model_templates`），原子写；`ui` 是自由字典（预算默认值、archive 的“忽略旧数据提示”都在里面） |
| `providers.json` | 明文、缩进 2 的 JSON：`{"schema_version": 1, "providers": [{id, name, protocol, base_url, models[{id, input_price_per_m, output_price_per_m, cache_read_price_per_m, cache_write_price_per_m, context_window_tokens, price_source}], read_only, source, auto_append_path}]}`——**没有 `api_key`**（文件里意外出现的 `api_key` 读取时忽略并告警，下次写入时丢掉）；环境变量 Provider 从不落盘；`source` 只是标签（新建为 `user`；旧数据里的 `encrypted` / `legacy-migration` 原样保留）。`providers.backup.json` 是上一份好副本：当前文件读不出时回退，两份都不行 → `StorageError` |
| `secrets.v1.enc` | `app.storage.crypto` 的 AES-256-GCM 信封，用途串 `secrets.v1`，明文是 `{"schema_version": 1, "keys": {provider_id: api_key}}`；`SecretStore.write_all({})` 删除文件（不需要主密钥）；没有主密钥保存 key → `StorageError("不能保存 API Key：没有可用的主密钥…")`，什么都不写；密文读不出 → `StorageError("无法解密已保存的 API Key：…")`（不含密钥内容）。没有备份副本 |
| `pricing.json` | 价格表，内容与 v0.12.1 的 `pricing.v1.json` 相同，只改了文件名 |
| `games/<id>/game.json` | 明文 JSON（UTF-8、`ensure_ascii=False`、紧凑不缩进），存档格式 v5；`game.prev.json` 是上一份**完好**的副本（当前文件读不出就不轮换；内容与当前相同的保存不重写、不轮换） |
| `games/index.json` | `{"schema_version": 1, "games": [摘要…]}`（`updated_at` 新→旧）；每次保存更新；缺失 / 损坏 / 与目录的 id 集合不符 / 某条的 `size_bytes`·`updated_at`（取自 `game.json` 的大小与 mtime，UTC ISO）与文件不符时，`list_games()` 从各局文件重建并写回 |
| `logs/<id>/trace-*.jsonl` | 沿用 v0.12.1；`GameStore.delete(id)` 一并删除 |

所有写入走 `app/storage/_atomic.py`（临时文件 → fsync → `os.replace`，POSIX 上 0600 / 目录 0700）并回读校验；拒绝符号链接（`games/`、对局目录、`game.json`、`providers.json`、`secrets.v1.enc`、`.lock` 都不会被跟随或替换）。对局 id 沿用 `_validation.validate_session_id`（`^[A-Za-z0-9_-]{1,64}$`，拒绝 Windows 保留名）。

**`GameStore` 补充**（接口见 §11.3）

- `load()` 对“没有这局”抛 `GameNotFoundError`（`StorageError` 的子类，API 层答 404）；两份文件都读不出抛普通 `StorageError`（503）；非法 id 抛 `ValueError`（400）。读取 / 列出**从不创建**目录。
- 摘要里 `status` 还可能是 **`"unreadable"`**（两份文件都读不出：只能删除，其余字段取默认值，`schema_version: null`）；`schema_version != 5` 的对局照常出现在列表里（`load_game` 对它抛 `SessionLoadError`，文案 = `OLD_SAVE_NOTICE`）；摘要的 `session_id` 取文件夹名（文件里的 `session_id` 与之不符时 `load_game` 拒绝载入）。
- `delete()` 先检查符号链接再动手；`list_games()` / `rebuild_index()` 只认合法 id 的文件夹，跳过符号链接和没有对局文件的文件夹。

**编排器（`SessionRuntimeMixin`）**

- 注入点 `game_store`（`GameStore` 或同接口的假对象；旧名 `session_store` 是同一个属性的别名，旧测试照常能用）；`_sessions()` → `_games()`。`tests/game_fakes.py` 的 `FakeGames`（别名 `FakeSessions`）实现 `save` / `load`（缺失抛 `GameNotFoundError`）/ `exists` / `delete` / `list_games`。
- `async load_game(session_id) -> GameSession`：校验 id（`ValueError`）→ 对局进行中 `RuntimeError`（409）→ 要载入的就是当前对局则原样返回 → 读文件（`GameNotFoundError` / `StorageError`）→ 校验 v5（`SessionLoadError`，含“id 与文件夹不一致”）→ 保存当前对局（`persist_session("pre-load-game")`，**失败则抛出、当前对局不变**；恢复保护模式下不保存那局空白占位）→ 暂停并采用新对局（`restore_notice` = `已载入对局（已暂停）`）→ 广播 `snapshot`（`session_loaded`，随后自动保存使它成为 `last_session_id`）。
- `async reload_from_data_dir() -> GameSession`：对局进行中或赛后复盘正在写名册时 `RuntimeError`；在 `persistence_suspended()` 里（块内外都能调）清各单例缓存、重建 LLM 客户端（界面选的 reasoning effort 保留，旧客户端关闭）、重读配置 / 名册 / 设置 / 绑定，恢复 `last_session_id` 指的对局为暂停（没有或文件已不存在 → 新建一局，文件已不存在时 `restore_notice` = “上次的对局文件已经不存在…”，不进恢复保护模式；文件损坏 → 恢复保护模式，文件原样保留）；**不保存旧对局**；最后广播 `snapshot`。
- `async with persistence_suspended():`（给 archive 整体替换数据目录用）：进入时取消防抖定时器、等正在进行的写完成、持有保存锁；块内 `schedule_autosave` 丢弃请求（不排队、结束后不重放），`persist_session` 抛 `RuntimeError`（`raise_errors=False` 时返回 `False`），`flush_autosave` 返回 `False`；可重入；异常退出也会复原。
- 时间戳（F22）：`created_at` 在新建时写（`GameSession` 默认值）；`started_at` 在**第一次**开始 / 继续时写（已有则不动）；`finished_at` 在对局结束时写，**继续**已结束的对局时清为 `null`。`app.game.session.utc_now_iso()` 是统一的取时间函数。
- `_restore_last_session`：`schema_version != 5` → 文件保留、新建一局、`restore_notice = OLD_SAVE_NOTICE`（“…请用 tools/migrate_v0121_to_archive.py 转换后导入。”）；缺失 → 新建一局 + 提示（无恢复保护）；其它读 / 校验失败 → 恢复保护模式（`_recovery_pending`：不自动保存，文件原样保留）。
- `app/game/demo.py::install_demo` 不再替换 `providers.binding_issues` / `routes._require_complete_bindings` 这两个**进程级**函数（以前会污染同进程里的其它测试）；API 层改为看 `orchestrator.demo_mode`。

**Provider 与 key（`ProviderStore`、API）**

- `ProviderConfig.api_key` 默认 `""`（“未设置”）。`create_provider(..., api_key="")` 创建没有 key 的 Provider；`HTTP POST /api/providers` 仍要求非空 key（界面表单必填），没有 key 的 Provider 来自导入存档（F32）。
- `update_provider`：只有 Provider **已有 key** 时，改协议 / 地址 / 自动拼接路径才必须同时给新 key（`PATCH` 同规则，400）；没有 key 的可以直接改。key 先写（`secrets.v1.enc`）再写注册表；写注册表失败会回收刚写的 key；每次写 key 顺带清掉已不存在的 Provider 的 key；`delete_provider` 同时删 key（key 文件读不出时跳过，不动它）。
- **读取宽松、写入严格**：key 文件读不出时 `list_providers()` 照常返回注册表（`api_key` 全为 `""`），`ProviderStore.keys_error` 给出原因（`None` = 正常）；**保存新 key 才报错**（503，旧文件原样保留，绝不覆盖）。
- “未设置 API Key”：`compute_binding_issues`（开始前的检查）与 `GET /api/state` / `/api/settings/bindings` 的 `issues` 对用到没有 key 的 Provider 的角色报 `Provider「<名称>」未设置 API Key`（key 文件读不出时 `compute_binding_issues` 另加“已保存的密钥无法解密：主密钥缺失或不匹配”）。
- 环境变量 Provider（`DEEPSEEK_API_KEY`，`id = env-deepseek`，只读）行为不变，不依赖主密钥。

**Docker**：镜像里程序目录是 `/app`，默认数据目录就是 `/app/data`（`VOLUME`，属主 uid 10001，0700），**不设** `ARENA_DATA_DIR` / `ARENA_WORKSPACE_DIR`；compose 新卷名 `arena-appdata`（`ARENA_DATA_HOST` 可换成宿主机目录）、主密钥 secret 保留（`ARENA_MASTER_KEY_FILE=/run/secrets/arena_master_key`）；旧卷 `arena-data` 不使用也不删，升级见 [storage.md](storage.md)。

### 11.7 接管与输入框细节（takeover 补全）

决策 F1–F19。接管是**服务端状态**（`GameSession.takeover`，随对局保存）；动作者永远由服务端决定，客户端不能替别的座位操作。

**座位状态 `seat_status(world, seat)`（`app/world/seat.py`，引擎中立的纯函数）**——与 `speech_gate` 完全一致（`tests/v12/world/test_seat.py` 把它和 `speech_gate`、状态板、真实的 `speak` 逐频道锁在一起），界面只画它、不自己推算发言规则：

```jsonc
{
  "seat": "N3", "seq": 418,                 // seq = 算这份状态时的账本序号：人类草稿的 based_on_seq 以它为准
  "channels": {                             // 座位所在的每个频道（含系统私聊），键是频道 id
    "public": {
      "can_write": true,                    // 此刻 speak 能不能通过提交闸门（不含“对局是否在运行”：界面自己显示“已暂停 / 未开始”）
      "why_not": null,                      // 不能时一句中文原因（昵称，没有内部 id），可直接做悬停提示
      "code": null,                         // 不能时闸门的拒绝码（NO_FLOOR / CHANNEL_CLOSED / QUOTA_EXCEEDED …）
      "max_chars": 300,                     // 一条消息的字数上限（超出被截断，不是拒绝）；不能发言时为 null
      "floor": {                            // 令牌（轮流 / 队列）或自由讨论的额度；其余频道为 null
        "kind": "queue|turn|free", "mine": true, "paused": false,
        "messages_left": 2, "chars_left": 560, "seconds_left": 87.5, "deadline_clock": 215.9
      },                                    // free：mine 恒为 false，messages_left 是我还能发几条，其余为 null
      "can_pass": true                      // pass（结束发言）能不能成功：持有活跃令牌，且频道没冻结、发言组没暂停
    }
  },
  "requests": [                             // 发给该座位、仍 open 的请求
    {"id": "r3", "kind": "choice|text", "max_chars": null,   // text：答案按它截断
     "answered": false, "my_answer": null,                    // 或 {"value","label","reason"}（可以改答，以最后一次为准）
     "seconds_left": 52.0, "deadline_clock": 190.4,           // deadline_clock：绝对游戏时钟秒，前端用它和 clockNow 倒计时
     "channel_id": "public"}                                  // 请求卡片出现的频道（同 view.js requestChannelId 的规则）
  ],
  "abilities": [                            // 此刻启用、该座位持有、次数没用完的技能（按剧本 abilities.<id>.params 生成表单）
    {"id": "…", "description": "…", "quota_left": 1,
     "params": [{"name": "target", "type": "player_id", "optional": false, "candidates": ["N1", …]},
                {"name": "declaration", "type": "text", "optional": false, "max_chars": 120}]}
  ],                                        // params 的 type：player_id / player_ids（candidates = 未出局的玩家）/ text（max_chars）/ enum（values）/ int（min、max）
  "attention": ["public"]                   // 待你操作的频道：我持有可用的发言权，或有一张没作答的请求卡片出现在那里
}
```

**`PublicSession.takeover`**（`orchestrator.takeover_payload()`）：`{"seat": null, "reshuffle_available": bool}`（没有接管），或 `{"seat": "N3", "reshuffle_available": bool, …上面的座位状态（不含重复的 seat）}`。`reshuffle_available` = 对局 `idle` 且没有开始记录（`started_at` 为空、账本里没有 `game.status = running`）——重新发牌提醒条只在它为真时出现（F5）。参与者的 `state` 在接管期间是 `"human"`（前端画“🎮 人类操作中”；`sleep_until` 为 `null`；`agent.status` 改不掉它，暂停也不会把它变成 `sleeping`）。座位状态算不出来时（`seat_status` 出错）**失败即关闭**：仍是 `{"seat", "reshuffle_available", "seq", "channels": {}, "requests": [], "abilities": [], "attention": []}`（界面显示“禁言中”），错误写日志，不会让 `/api/state` 或 SSE 快照整个失败；存档里的座位在游戏里不存在时按“没人接管”处理。

**`takeover.updated`**：`data = {"takeover": <PublicSession.takeover>}`。接管 / 退出时**一定**发布一次；其余时候，**除** `takeover.updated` 自己、`agent.metrics`、`budget.*` 之外的任何 UI 事件（`message.committed`、`floor.changed`、`request.*`、`ability.used`、`channel.*`、`player.updated`、`game.status`、`phase.changed`、`agent.status` ……）之后，**合并**（同一个事件循环 tick 内最多一次）重算，内容与上一次发布的相比有变化才发布（比较时忽略逐秒变化的 `seconds_left`；`seq` 算内容，所以账本每前进一步都会推一次）；不进入 `AUTOSAVE_EVENT_TYPES`。`agent.status` 也算，是因为技能的启用 / 停用只写账本、没有自己的界面事件，主持人那一轮结束时的 `agent.status` 是它们之后第一个信号。倒计时不靠它：前端用 `deadline_clock` 与自己的 `clockNow` 数秒。换了一局（新建、载入历史、导入存档、重启恢复）时，客户端靠 `snapshot` 拿到整份 `takeover`，服务端忘掉上一局推过什么。

**接管 / 退出**（写接口都要 `require_trusted_client`；错误体 `{"detail": "中文说明"}`）：

| 接口 | 请求 | 成功 | 错误 |
|---|---|---|---|
| `POST /api/takeover` | `{"seat": "N3"}` | `{"ok": true, "session": PublicSession}`；再次接管同一座位是无操作 | 404 座位不存在；422 不是玩家座位（主持人）；409 对局运行中 / 已结束（只有 `idle` / `paused` 可以）、已经接管了另一个座位（“请先退出当前接管”） |
| `POST /api/takeover/release` | – | `{"ok": true, "session": PublicSession}`；没有接管时是无操作 | 409 对局运行中（请先暂停；`idle` / `paused` / `finished` 都可以退出） |

接管：`session.takeover.seat = seat`，追加 `HumanSpan(seat, from_seq=<世界 seq>, to_seq=None)`，该座位**不创建 agent**（`_build_runtime` 跳过它；仍须有模型绑定，F9），`agent_state[seat] = "human"`；投递给它的信封被监督器安静地丢弃（`Supervisor.pump`），看门狗只看有截止时间的世界计时器（人类持有的发言权 / 请求都有），不会误叫醒主持人；广播并 `schedule_autosave`。退出：`takeover.seat = None`，关闭对应的 `human_span`（`to_seq = <世界 seq>`），`ConversationBook.reset(seat)` + `brain.reset_conversation(seat)`——下一次继续对局时重建的 agent 以完整的首条消息（状态板 + 笔记 + 全部可见历史，其中有人类以它名义说过的话）开始；不告诉这个 agent 有人代打过（F6）。重启后：对局以“已暂停”恢复，`takeover` 与未关闭的 `human_span` 保留，该座位仍是 `human`；历史里的“继续”（`load_game`）和导入存档走同一条路（`_adopt_loaded_session` → `_sanitize_takeover`），行为相同。存档自相矛盾时在载入时修正：座位在这局里不存在 → 没人接管；不属于当前座位的未关闭 `human_span` → 在它的 `from_seq` 处关闭；有接管却没有未关闭的 `human_span` → 补一个。新建对局永远没人接管。重新发牌（`POST /api/control/shuffle-identities`）与“开始”、接管、退出共用同一把控制锁（`orchestrator._control()`），且在 `status != idle` 或已有开始记录时返回 409（F5）；重新发牌不换座位的接管状态。赛后复盘与战绩只依赖世界和模型绑定，被接管过的座位照常复盘（F8）。

**座位动作** `POST /api/seat/speak | pass | respond | ability`：动作者固定是 `session.takeover.seat`；构造 `Intent` 走与 agent 相同的 `world.submit`（轮次 / 字数 / 条数 / 截止时间 / `STALE` 全是引擎的规则）。

| 接口 | 请求体 | 说明 |
|---|---|---|
| `/api/seat/speak` | `{"channel_id", "content", "based_on_seq"?}` | `based_on_seq` 是**人开始写这条草稿时**看到的 `takeover.seq`（前端在草稿从空变成非空时记下；省略 = 当前 `world.seq`，永不过期；比当前还大的值按当前处理）。草稿期间发生了 `invalidates_drafts` 里的账本条目 → `STALE`。`content` 非空、至多 20000 字（超过单条字数上限的部分由闸门截断，不是拒绝） |
| `/api/seat/pass` | `{"channel_id"}` | 结束发言 |
| `/api/seat/respond` | `{"request_id", "value", "reason"?}` | 作答 / 改答（关闭前以最后一次为准） |
| `/api/seat/ability` | `{"ability_id", "params"}` | `params` 按技能的 `params` 定义；服务端用 `validate_params` 校验 |

- 成功与世界的拒绝都是 **HTTP 200**，body 是回执的精简形式：`{"accepted": bool, "seq": int|null, "code": str|null, "message": "…", "truncated"?: {"dropped_chars", "kept_chars"}, "data"?: {…}}`（`data`：`STALE` 的 `latest_seq`、`respond` 的 `replaced` / `closed`、`ability` 的 `uses_left` 等回执里的内容）。被拒绝时前端保留草稿并提示 `message`；`STALE` 时把草稿的 `based_on_seq` 更新为最新值，用户确认后再发一次就会通过。
- HTTP 错误：409 没有接管任何座位（“请先接管一个座位”）；409 对局没有在运行（“对局已暂停 / 未开始 / 已结束，不能操作”）；422 载荷无效（多余字段一律 422——`extra="forbid"`，所以请求里没有地方指定别的座位；`reason` ≤ 1000 字，`value` ≤ 2000 字，`based_on_seq` ≥ 0）；403 / 401 沿用 `require_trusted_client` / 令牌规则。服务端的 409 / 404 / 422 在编排器里是 `TakeoverError(message, status)`（`app/game/takeover_runtime.py`，`orchestrator` 也导出）；`/api/control/shuffle-identities` 把它映射成同样的状态码（其余 `RuntimeError` / `ValueError` 仍是 400）。

**不提供给人类的**：`speak_template`（直接打字）、笔记 / 文档类工具、质询按钮（用和主持人的私聊代替，F19）、`sleep`。猎人开枪是发给猎人的选择题请求（不是技能），以请求卡片出现。

**前端**（`static/js/takeover.js`、`composer.js`；`view.js` 的 `viewpointBar` / `takeoverBar` / `composerModel` / `requestAction` 等纯函数）：视角栏 `[视角▾][切换][接管]`（下拉框只改“待切换的视角”，点“切换”才生效；`god` 时“接管”不可用；只在 `idle` / `paused` 可用）；接管期间视角锁定为该座位（只在前端，F3），顶栏换成“🎮 正在扮演 3 · Carol [退出接管]”（手机上它顶替标题留在首行，不进 ⋯ 菜单），详情面板的“以 X 的视角观看”禁用（扮演的座位本人没有这个按钮）；重放中（`state.replay`）“接管”不可用；每频道一个输入框（草稿按频道保留，Enter 发送 / Shift+Enter 换行，计数取 `max_chars`）、发送按钮的五种状态（发送 / 禁言中 / 已暂停 / 未开始 / 已结束）、结束发言（`can_pass`）、技能（列表 → 按 `params` 生成的表单 → 二次确认）；请求卡片对该座位可点击；频道栏按 `attention` 画“待你操作”。输入框随文字增高（最高 148 px 后滚动；触屏设备的占位符不写 Shift+Enter）；手机软键盘弹出（`visualViewport`）时页面高度跟着缩，底部标签栏、状态胶囊和 6×2 小卡片让位给输入框。“接管”、“退出接管”、“重新发牌”、技能在点击处理函数里都会再核对一遍当时的状态（对局已经开始 → 不发请求，只提示原因），所以界面落后于服务端一拍也不会误操作。

### 11.8 历史与重放细节

**投影器（已实现并验证）** `app/game/replay.py: build_replay(payload) -> dict`，`payload` 是 v5 对局字典（`GameStore.load` 的返回值）：

```json
{"version": 1,
 "game": {"session_id", "title", "scenario_title", "status", "winner", "created_at", "finished_at", "human_involved"},
 "initial": <PublicSession：第一条账本之前的会话——座位已坐好但没有身份，没有频道 / 消息 / 请求>,
 "events": [{"seq": 12, "gt": 3.5, "type": "message.committed", "data": {…}}],
 "duration_gt": 123.4}
```

- `events` 按账本顺序；`seq` 是产生它的账本条目，`gt` 是那一刻的游戏时钟秒（暂停不走，所以重放的“时间轴”就是游戏时间）；`type` / `data` 与直播 SSE 一致，前端 `Store.applyEvent(session, {id, type, data}, {clockNow: gt})` 可直接消费。上帝视角下所有事件都在，视角过滤由前端按 `visible_to_ids` 等字段做（与直播相同）。
- **只含观战内容**：思考、工具调用、agent 状态（`agent.status` / `agent.metrics`）不在账本里，重放里没有；参与者始终是 `sleeping`。`initial.usage_stats` 是整局的最终合计（顶栏的数字在重放里是常数）；`initial.budget` 是空的（不显示预算）。
- 账本 → 事件的映射（投影器自己维护频道 / 发言权 / 请求 / 工单 / 玩家的模型，因为账本记录的是“事实”，前端要的是“视图”）：

| 账本条目 | 事件 |
|---|---|
| `message` | `message.committed`（= `projection.message_view`）；`kind=challenge` + `ticket_id` 再加 `challenge.opened`，`kind=reply` 再加 `challenge.resolved`；在发言权频道里按 `chat._account` 的规则累计 `messages_used` / 自由讨论的条数与字数后再发 `floor.changed` |
| `channel.created` | `channel.created`（数据就是 `channel_view`） |
| `channel.updated`（`changes`：`mode` / `limits` / `unfrozen` / `name` / `added` / `removed` / `readonly`） | `channel.updated` + `floor.changed` |
| `floor.opened` / `floor.granted` / `floor.token_ended` / `floor.completed` / `floor.paused` / `floor.resumed` / `floor.frozen` / `floor.closed` | `floor.changed`（`opened` / `completed` / `closed` / `frozen` / 解冻的 `resumed` 另加 `channel.updated`）；`seconds_left` 按 `gt` 与令牌的 `duration_s` 算出（暂停时是冻结值） |
| `request.opened` | `request.opened`（`seconds_left` = `duration_s`） |
| `request.answered` | `request.progress` + `request.answer`（`visible_to_ids` = 条目的受众，密封请求为 `[]`） |
| `request.closed` / `request.cancelled` | `request.closed`，再加一条 `request.updated`（完整的请求视图，含默认答案——与新快照一致） |
| `player.updated` | `player.updated {player_id, tags, out}`（`tags` = `tags_after`；`out` 按 `ui.out_tags`）；发牌也是这条，所以重放开头会“发身份” |
| `phase.changed` / `dashboard.updated` / `ability.used` / `game.status` | 同名事件（`game.status` 的 `winner` 非终局时为 `null`） |
| 其余（`ability.enabled|disabled`、`player.public_changed`、`random.drawn`、`request` 之外的 `request.*` 的不可见细节） | 不产生事件 |

- **验证**：`tests/v12/world/test_replay.py` 在真实 `World` 上走一局脚本（发言权的 turn / queue / 暂停 / 冻结 / 超时 / 关闭、自由讨论、成员与只读、四种请求、质询、技能、出局、看板、终局，共 51 步），**每一步**都把直播事件和投影事件比较（消息逐条相等；频道按前端 `Store` 的方式折叠后逐个相等；请求 / 玩家 / 阶段 / 工单 / 状态事件逐条相等）；`tests/test_replay_client.py` 把一整局演示对局投影后用**真实的** `static/js/store.js` 应用，最终状态与服务端的 `public_session()` 一致（`tests/frontend/replay_projection_check.js`）。
- 体量：约 650 字节 / 条账本（演示局 277 条 → 404 个事件、180 KB），3000 条的真实对局约 2 MB；一次返回完整事件流，不分页。

**HTTP（`app/api/games.py`，已实现）**

| 接口 | 响应 / 错误 |
|---|---|
| `GET /api/games` | `{"games": [摘要 + "current": bool], "current": "<live id>"}`，最近保存的在前；当前对局还没落盘时也会出现在列表里（第一项，由 `session_payload()` 现算摘要） |
| `DELETE /api/games/{id}`（写接口） | `{"ok": true, "session_id"}`；当前对局 409“当前对局不能删除”；不存在 404；id 非法（含 Windows 设备名）400。只删 `games/<id>/` 与 `logs/<id>/`，**不碰名册**（性格与记忆属于座位，不属于某一局） |
| `POST /api/games/{id}/load`（写接口） | `{"ok": true, "session": PublicSession}`（先保存当前对局，载入的对局保持已暂停）；就是当前对局 409；不存在 404；`RuntimeError`（对局进行中、当前对局保存失败）409；`SessionLoadError`（存档无法打开）400 |

**前端（`static/js/history.js`、`replay.js`，已实现）**

- 历史对局窗口（`#history-modal`，按钮 `#btn-open-history-modal` 取代旧的“会话”）：每行由 `History.rowModel(game, env)` 决定显示与按钮是否可用（纯函数，有测试）；`env` = 当前对局的 `{status, takeoverSeat, replaying}`。三个操作在**点击时**再核对一次条件（渲染之后状态可能变了），删除 / 载入先确认；删除确认的文案必须含“删除对局不会影响当前 agent 的记忆”。
- 重放模式的隔离：重放用**独立的会话**（`Store.normalizeSession(initial)` + `Store.applyEvent`），`app.js` 在重放期间让 `state.session` 指向它（所有渲染器因此不用改），直播的会话暂存在 `state.replay.live`；SSE 事件照常到达，但 `handleEvent` 在重放期间把它们应用到 `state.replay.live`，什么也不画，直播的快照 / HTTP 应答也只替换 `live`；“退出重放”换回 `live`，界面就是此刻的直播。重放的会话带 `session.replay = {title, session_id, duration_gt}`，`View.controlState` / `View.takeoverAvailability` 据此禁用开始 / 暂停 / 继续 / 新建 / 接管，状态行显示“重放中 · 0:41 / 2:30”。
- 播放条的时钟：把同一条账本记录的事件合成一步（`buildSteps` 按 `seq`）；两步之间等 `Δgt ÷ 倍速` 秒，“跳过空闲”（默认开）把超过 5 个游戏秒的间隔压成 0.5 秒，且不少于 0.12 秒（`stepDelayMs`）——真实对局的 `gt` 是秒级，演示局和模拟服务的 `gt` 几乎为 0，没有下限整局会一闪而过；倍速 0.5 / 1 / 2 / 4 / 8，改倍速或开关“跳过空闲”立即替换正在等待的那个定时器。进度条的单位是“步”；向前拖只补应用缺的步，向后拖从 `initial` 同步重建（一个循环，不逐帧），拖动后接着播放。
- 模拟服务（`tools/mock_ui_server.py`）：`/api/games*` 与上面一致；列表是当前对局 + 三个虚构的旧对局；重放是把脚本在虚拟时间里离线演一遍（`history_replay()`，在工作线程的独立事件循环里），裁到 `REPLAY_EVENT_TYPES`（没有 `agent.*` / `budget.*` / `review.*`），`seq` 取事件 id，`gt` 取发出那一刻的游戏时钟；载入旧对局只是发一个带请求 id 的新局（模拟服务不能真的还原）。

### 11.9 存档细节（archive 补全）

> 代码是权威；格式、加密、流程和转换脚本的完整说明见 [archive.md](archive.md)。以下是跨流需要依赖的确切行为。

**包 `app/archive/`**：`format.py`（常量、路径白名单 `classify()`、`Manifest` 模型、`files_digest()`、`ArchiveLimits`）、`kdf.py`（密码规则与 `seal_secrets` / `open_secrets`）、`export.py`（`export_archive(data_dir, ExportOptions, …) -> ExportResult`，阻塞，放进线程）、`importer.py`（`inspect(path) -> ArchiveSummary`、`prepare` / `commit` / `apply(path, password, skip_keys, …)`、`decrypt_archive_keys`）、`jobs.py`（`ArchiveManager`：一个导出 / 导入任务、上传会话、进度事件）、`legacy.py`（旧数据提示）、`ports.py`（对编排器的窄接口）、`errors.py`。所有错误是 `ArchiveError` 的子类，带用户可读的中文 `message`、机器可读的 `code` 和 HTTP `status`；**任何错误文本都不含密码、Key、文件内容或服务器路径**。

**容器与清单**：zip，成员路径白名单见 archive.md §1.1（`manifest.json`、`settings.json`、`providers.json`、`pricing.json`、`roster/…`、`games/index.json`、`games/<id>/game.json|game.prev.json`、`logs/<id>/trace-NNNN.jsonl`、`secrets.enc`）。`manifest.json` 最后写入：`{"format": "arenaagents", "format_version": 1, "app_version", "archive_id": <32 位小写十六进制>, "created_at": <带时区的 ISO-8601>, "contents": {"games", "providers", "roster_seats", "has_secrets", "has_logs"}, "files": [{"path", "size", "sha256"}…按路径排序, "files_sha256"}`；`files_sha256` = 清单（按路径排序、每项 `{"path","sha256","size"}`、`sort_keys`、紧凑、`ensure_ascii=False`）的 SHA-256。校验顺序（archive.md §1.3）：zip 与条目数 → 成员名与限制 → 清单（**更新的 `format_version` 先被拒绝并提示升级**）→ 清单与成员一一对应 → 逐个成员的大小与 SHA-256 → 内容（对局 = 存档格式 v5 + `GameSession`；`providers.json` 不得含 `api_key` 字段）→ 统计一致。

**`secrets.enc`**：JSON `{"format", "version": 1, "kdf": "scrypt", "n": 131072, "r": 8, "p": 1, "salt", "cipher": "aes-256-gcm", "nonce", "aad", "ciphertext"}`（字节串是 base64；参数固定，别的值被拒绝）。密钥 = `scrypt(NFC(密码), 盐 16 字节, n=2**17, r=8, p=1)` → 32 字节；AES-256-GCM，12 字节随机 nonce；明文 `{"schema_version": 1, "keys": {provider_id: api_key}, "endpoints": {provider_id: {"protocol", "base_url", "auto_append_path"}}}`（**每个 Key 与它的 Provider 地址封在一起**）；AAD = `{"archive_id","format","format_version","purpose":"secrets"}`（`sort_keys`、紧凑 JSON）。密码错误 / 被改动 / 别的存档的文件 / 头部损坏 → **同一个** `ArchivePasswordError`（“密码错误或 API Key 部分已损坏”，`code = wrong_password`，422）。密码对、但 `providers.json` 里某个有 Key 的 Provider 的地址与密文里的不一致（`providers.json` 不加密，改它就能把 Key 引到别处）→ `ArchiveKeysMismatchError`（`code = keys_mismatch`，422，**不导入任何 Key**，上传保留，可改选“跳过 API Key”）；密文里没有地址同样按不一致处理。新密码规则（`kdf.password_problem`，前端 `archive.js` 同一规则，共用 `tests/archive/password_cases.json`）：NFC 后 12–256 个字符、无控制字符、大写 / 小写 / 数字 / 符号至少三类（其余字符都算符号）。

**任务与进度**：同一时间只有一个任务（导出、上传 + 校验、导入）；再开 → 409 `busy`。进度由 `ArchiveManager` 经 `orchestrator.bus.publish(UiEvent(type="archive.progress", data=…))` 发出，`data = {"job_id", "kind": "export"|"import", "phase", "done", "total", "status": "running"|"done"|"error", "message"?, "code"?, "result"?}`；`done` / `total` 在 `pack` 与 `verify` 阶段是字节，其余阶段是步数。导出阶段 `flush → collect → encrypt → pack → finalize`；导入阶段 `verify → validate → backup → replace → keys → reload → finalize`。`result` 不含服务器绝对路径（`GET /api/archive/jobs/{job_id}` 对本机请求的导出结果多一个 `path`）。上传校验期间的 `verify` 事件用 `import_id` 作 `job_id`（`kind = "import"`）。

**接口细节**（鉴权同 §11.5；错误 `{"detail", "code"}`）：

| 接口 | 请求 → 响应 |
|---|---|
| `POST /api/archive/export` | `{"include_keys": bool, "password"?: str, "include_logs": bool = true}`（多余字段 422；密码最长 1024）→ 202 `{"job_id", "kind": "export"}`；含 Key 而密码不合规 → 422 `weak_password`；已有任务 → 409 `busy`。先 `flush_autosave("pre-export")`（对局进行中也允许），保存失败只是警告 |
| `GET /api/archive/status` | `{"busy", "job": 进行中的任务快照 \| null, "import": 等待决定的上传 \| null, "game_active"}` |
| `GET /api/archive/jobs/{job_id}` | 事件的形状；导出完成时 `result = {"name", "path"?(仅本机), "display_path": "data/exports/<name>", "size_bytes", "archive_id", "created_at", "app_version", "contents": {…}, "file_count", "uncompressed_bytes", "warnings": [...]}`；未知 → 404 `not_found` |
| `GET /api/archive/exports/{name}` | 文件（`application/octet-stream`，`Content-Disposition: attachment`）；`name` 只能匹配 `^arena-[0-9]{8}-[0-9]{6}\.arenaagents$` 且是 `data/exports/` 里的普通文件（不是符号链接），否则 404；下载链接发不出请求头，所以**仅此接口**额外接受 `?token=` |
| `POST /api/archive/import?name=…` | 请求体 = 文件；流式写 `data/tmp/`（不读进内存），声明的或实际的大小超过 `ARENA_MAX_ARCHIVE_BYTES`（默认 2 GiB）→ 413 `too_large`；对局进行中 → 409 `game_running`；校验失败 → 422 `invalid_archive` / `unsupported_version`；成功 → `{"import_id", "name", "size_bytes", "summary": {"archive_id", "format_version", "app_version", "created_at", "size_bytes", "uncompressed_bytes", "file_count", "games", "providers", "roster_seats", "has_secrets", "has_logs", "provider_names": [...], "game_list": [{"session_id", "title", "scenario_title", "status", "winner", "created_at", "human_involved", "players"}…最多 100 条], "games_listed", "warnings": [...]}, "expires_in": 秒}`。新上传取代上一份；2 小时无操作过期 |
| `POST /api/archive/import/{import_id}/apply` | `{"password"?: str, "skip_keys": bool = false}` → 202 `{"job_id", "kind": "import"}`。含 Key 且没有 `skip_keys`：缺密码或密码错 → 422 `wrong_password`（**同步**检查，不开任务，上传保留，可重试，最多 10 次后丢弃并 429 `too_many_attempts`）；Key 与 Provider 地址不一致 → 422 `keys_mismatch`（同样同步、上传保留）；会话不存在 / 过期 → 404；对局进行中 → 409 `game_running`。任务完成 `result = {"backup": "<时间>"\|null, "games", "providers", "keys_imported", "keys_kept", "providers_without_key": [Provider 名…], "warnings": [...]}` |
| `DELETE /api/archive/import/{import_id}` | `{"ok": true, "discarded": bool}`，删除上传的文件 |
| `POST /api/notices/legacy-data:dismiss` | `{"ok": true}`；写 `settings.json` 的 `ui.legacy_data_dismissed = true`（`SettingsStore.get_ui_pref / set_ui_pref`） |
| `GET /api/state` | 新增 `legacy_data = {"found": bool, "dismissed": bool, "path"?: str}`；`found` 仅当数据目录“空”（没有 `providers.json`，`games/` 里没有东西）且默认位置有 v0.12.1 工作区（Windows / macOS `~/Arena-Agents/Default`，Linux `~/.local/share/Arena-Agent/workspace/default`，含 `.arena-workspace.json` 与 `.arena/`）；`path` 只给本机请求 |

**导入的替换事务**（`importer.commit`，在 `async with orchestrator.persistence_suspended():` 里，放进工作线程；`reload` 用 `run_coroutine_threadsafe(orchestrator.reload_from_data_dir())`）：① 解压到 `data/tmp/import-<id>/stage/`，边解压边再校验，解压文件的修改时间 = 导出时的修改时间；`settings.json` 必须被 `SettingsStore` 接受，其 `last_session_id` 指向存档里没有的对局时清空；② 把数据目录顶层条目（**除** `.lock`、`master.v1.dpapi`、`backups`、`exports`、`tmp`）整体改名搬到 `data/backups/<YYYYmmdd-HHMMSS[-n]>/`，并复制一份 `master.v1.dpapi` 进去；③ 把 stage 的条目搬进数据目录；④ Key：保留本机与存档 Provider **同 id** 的 Key，再叠加存档里解开的 Key（`SecretStore.write_all`；没有 Key 要写则不碰密钥库）；⑤ `clear_store_caches()` + `reload_from_data_dir()`；⑥ 删临时目录，只保留最近 3 份备份。任一步失败：把新条目移走、备份条目搬回、再清缓存并 reload 一次，原样抛出错误；回滚中无法还原的条目只记日志，备份文件夹保留。`reload_from_data_dir` 抛 `RuntimeError`（对局进行中 / 复盘进行中）→ 任务以 `game_running` 结束，文案用编排器自己的中文。

**转换脚本 `tools/migrate_v0121_to_archive.py`**：`--workspace`（默认 `detect_legacy_workspace()`；也接受 `.arena` 目录）、`--output`（默认 `./arena-v0121-<时间>.arenaagents`，已存在或位于旧工作区内 → 退出码 2，不覆盖）、`--include-keys`（`getpass` 两遍，规则同 `kdf.password_problem`，三次机会）、`--no-logs`。只读：用 `app.storage.crypto.decrypt_json(…, "providers.v1" | "session.v1:<id>", data_dir=<…/.arena>)` 读旧数据，缺主密钥（Windows 无 `master.v1.dpapi` 且没有 `ARENA_MASTER_KEY[_FILE]`）时直接报错，**不创建**密钥文件。对局 v4 → v5：`schema_version = 5`、`takeover = {"seat": null}`、`human_spans = []`、`created_at` = 账本第一条的 `ts`、`started_at` = 第一条 `game.status` 为 `running` 的 `ts`、`finished_at` = 最后一条 `finished` 的 `ts`（其后又 `running` 则 `null`）（UTC）；格式 < 4、解密失败、不符合 v5 的对局跳过并列入报告；`providers.v1.enc` 解密后去掉 `api_key` 与环境变量 Provider（`read_only` / `source == "environment"`）写成 `providers.json`；`pricing.v1.json` → `pricing.json`；只拷名册（`roster.json`、`N<k>.persona|memory.md`）。报告写 stdout（转换了几局、跳过的 id 与原因、Provider 数、是否带 Key、日志是否包含、输出路径与大小、提示），**不打印任何 Key**；错误写 stderr，退出码 `0` / `1`（出错）/ `2`（参数）。

**模拟服务**（`tools/mock_ui_server.py`，`MockArchive`）：以上接口都有，任务真的“走”一遍阶段（约 2 秒，随 `--speed` 变快）并发 `archive.progress`；上传文件的**名字**决定走哪条分支（`demo` 正常、`keys` 含 Key 且密码 `Correct-Horse-9`、`mismatch` 密码对但 Key 与地址不一致、`fail` 导入中途失败、`newer` 版本太新、`corrupt` 校验失败、`huge` 太大；别的文件按真实存档读它的 `manifest.json`，不是存档则 422）；`--legacy`（或 `POST /api/mock/archive {"legacy": true}`）显示旧数据提示条。
