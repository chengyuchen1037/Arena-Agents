## 0. 目标

v0.14 重写**玩家 bot 的结构**。多 agent 框架（World / Runtime / Supervisor）基本不动。要实现两个愿景：

1. **风格多样**：即使所有座位用同一个模型，各玩家的发言风格也明显不同，不再像写工作报告那样分点。
2. **抓住核心逻辑**：依据硬事实做判断，而不是被“讲得有条理”的表面发言带走。

具体做八件事：

1. **Bot 成为一等实体，与座位解耦**：bot = 名字 + 头像 + 分层记忆 + 初始化记录；座位只是这一局坐在哪里，开局前可以拖动调整。身份牌在点击“开始”时才发，开局前不存在、也不显示任何身份信息。
2. **四层记忆**：底层（L0：身份、说话方式、分析方式）、架构（L1：官方契约 + 自己的操作笔记）、规则（L2：官方剧本 + 自己的规则要点、打法、待解问题）、对局（L3：本局能接触到的一切）。每层都可以单独导入、导出、清除。
3. **编排器（Composer）**：按“挂载计划”把各层放到固定位置、控制预算，在做决定的那一刻把相关的层提到眼前，保证每一层都起作用、不被淹没。
4. **初始化**：bot 根据自己的底层设定，自己阅读契约和规则，写出操作笔记、规则要点和打法。提示词里不教打法。
5. **赛后复盘**：终局后弹窗询问；每个 bot 最多 60 秒自由复盘，修订自己的记忆；人类接管的发言作为学习素材。
6. **发言只由 bot 自己产生**：发言只能是 bot 的 worker 在（可以多轮的）思考之后自己调用 `speak`；引擎和编排器不代发、不改写、不截断。超长不再截断，而是退回让它自己重写（人和 bot 都一样）；不再要求“思考要简短”。
7. **存档管理重做**：设置对话框分五栏（总存档 / 底层设定 / 官方契约 / 规则 / 对局管理）；文件命名统一；总存档包含全部文件。
8. **基准（bench/）**：仓库内提供可复现的基准套件，作为本版验收的依据。

不做：主持人 bot 化（H46）；“教练 agent”（用自然语言改 bot 记忆，接口留好，放到 v0.14.x）；bot 池或替补（本版固定 12 个玩家位）；新剧本；新 Provider 协议。

### 1.3 编排器（Composer）

| # | 决策 |
|---|---|
| H12 | **挂载计划**（对局中的玩家），顺序与预算如下：<br>① system 开头：`identity` + `voice`（L0，≈ 900 字）<br>② `mind`（L0，≈ 400 字）<br>③ 我对这个游戏的理解：`digest` + 把握度为“中”或“高”的 `playbook` 条目（L2，≈ 1600 字）<br>④ 我对在座各位的印象（L2，≤ 11 × 80 字）<br>⑤ 官方规则（剧本中的玩家规则，参考用）<br>⑥ 平台怎么运作：契约“必读”段 + `arch/notes`（L1，≈ 2000 字）<br>⑦ system 末尾：身份锚 + 说话方式锚（L0，≈ 80 字）<br>tools 参数：官方工具（引擎生成）。首条用户消息与之后的增量消息：L3。 |
| H13 | **渲染方式**：bot 自己的记忆用第一人称写成段落。存储可以结构化，但渲染成散文，例如“我比较有把握的是……我还不太确定的是……”，避免分点模板反过来教模型分点。官方契约和规则用中性陈述。 |
| H14 | **事件提示**（追加在增量消息里，不破坏前缀缓存）：<br>• 轮到发言时：说话方式提示（`voice` 首句 + 篇幅区间），加上按情境标签检索出的 1–2 条打法，再加一句“先想清楚此刻最关键的一两件事，再一次说完整”。<br>• 收到投票或选择请求时：“你认定的最硬的事实是什么”。<br>• 收到夜间行动请求时：检索与身份相关的打法。<br>情境标签由剧本声明，例如在 `situations:` 里把阶段 / 请求类型映射到“对跳、警上、投票、夜晚、遗言、狼队”等标签；引擎只做映射与检索。 |
| H15 | **输出闸门**（只对 bot）。**闸门只退回、从不改写**：被拦下的发言不进频道，回执说明原因，由 bot 自己决定怎么改、再调用一次 `speak`。<br>• 格式闸：连续 2 行及以上的编号、列表或 markdown → 退回，回执码 `FORMAT`，提示“这是当众说的话，请改成连贯的口语”。<br>• 开头自报座位或名字（如“N3：”）→ 同样以 `FORMAT` 退回。<br>• 超长 → `TOO_LONG` 退回（H16）。<br>`FORMAT` 在同一个发言权内只退回一次，第二次照原样发出（避免卡住发言）。参数取自 L0：默认不允许分点，`voice.md` 可以声明 `允许口头列举`。 |
| H15a | **可观测**：每次模型调用在 trace 里记一份挂载清单（块 id、内容哈希、字数），不记正文；正文在 bot 文件与存档快照里可查。基准据此按层做消融。 |

### 1.4 发言流程

| # | 决策 |
|---|---|
| H16 | **超长退回，不截断**（所有发言者）。超过单条上限 → 拒绝，回执码 `TOO_LONG`，**不消耗发言权**；回执给出实际字数和上限。人类输入框实时计数，超限时禁用发送（服务端仍校验）。**每次超长都退回，不限次数，引擎从不截断玩家的发言**；发言权的时限照常计算，时限到了按超时结束（与现在一致）。主持人的 `send_message` 维持现状（截到 2000 字）。替换 D19 中“截掉”的部分。 |
| H17 | **额度与提示**：<br>• 单条上限**保持 300 字**（C12），剧本额度不改；配合 H16，超长的发言退回重写。<br>• 状态板的自由讨论显示单条上限。<br>• `max_messages = 1` 时不再显示“总共 ≤ N 字”。<br>• `speak` 的 schema 去掉 `maxLength: 20000`。<br>• 契约里不再有“思考要简短”；输出被长度上限截断时的提示改为“上一次输出因长度上限中断，请直接完成当前待办”。 |
| H18 | **发言流程：只能由 bot 自己的 worker 发起**（C14）。<br>• 轮到发言时，引擎只送达唤醒消息（含发言权信息和 H14 的事件提示）。bot 在这次唤醒里可以多轮思考：读笔记、写笔记、再想，然后自己决定调用 `speak` 或 `pass`。没有轮数限制，只受发言权时限约束（沿用 v0.12.1 的 worker 循环）。<br>• 引擎、编排器和任何外部程序**都没有代发路径**：不生成、不改写、不截断 bot 的发言，也不会用另一个模型调用把要点“转写”成发言。删除此前讨论的 `single` / `think-talk` 两种管线以及 `bots.speech_pipeline` 配置项。<br>• 编排器只负责准备 bot 看到的上下文（H12–H14）；闸门只退回（H15、H16）。 |

| H21 | **产出**：`arch/notes.md`、`rules/<scenario>/digest.md`、`playbook.md`（必需），`questions.md`（可选）。已经有这些文件时是**修订**而不是覆盖，保留复盘学到的东西。提示词只要求“用你自己的话写下你的理解、你打算怎么玩、你还不确定什么；这些都是假设，以后用结果检验”，**不给任何打法**。 |
| H22 | **初始化记录**写在 `bot.json` 的 `init` 字段：状态、时间、模型、耗时、错误，以及 `core_hash`、`contract_hash`、`scenario_hash`、`materials_hash`。状态有五种：未初始化、初始化中 ⏳、已初始化 ✔、需重新初始化 ⚠（L0、契约、剧本或材料变了，哈希对不上）、失败 ✖。卡片名字旁显示对应符号。 |
| H23 | **冻结**：初始化成功后，名字和头像冻结，详情面板显示 🔒。点“修改”会弹窗：“修改名字或头像会清空这个玩家的初始化结果和全部记忆（操作笔记、规则要点、打法、待解问题、印象、战绩），底层设定保留。修改后需要重新初始化才能开局。是否确认？”确认后直接清空（不保留副本，C9），换新的内部 id（名字变了就是新身份），状态变为“未初始化”。未初始化的玩家改名或改头像不弹窗。其他 bot 对旧名字的印象保留（不在座就不挂载）。替换 G31 中“对局未开始即可改”的部分。 |
| H24 | **用量**：初始化与复盘的调用记入错误日志，角色标为“初始化”或“复盘”。初始化不属于任何对局，单独显示“学习用量”；复盘计入那一局的预算（沿用 v0.13）。 |

### 6.1 离线测试（pytest，不联网）

- **超长退回**：
  - 人和 bot 超长都得到 `TOO_LONG`，发言权不消耗；

### 6.4 实机冒烟

用真实模型完成一次全局初始化 + 一局完整对局 + 复盘（含一段人类接管），检查：

- 初始化用时与失败率；
- 截断数为 0；
- 发言形态有可见变化；
- 复盘改动合理。

| 套件 | 验证什么 | 方法 | 指标 |
|---|---|---|---|
| R 运行健康 | 超长退回与运行状况 | 固定局面 + 整局 | 截断数（应为 0）、`TOO_LONG` / `FORMAT` 退回次数、退回后一次重写成功率、发言权超时率、工具拒绝率、发言耗时、每局 token、初始化成功率与用时 |
| S1 发言形态 | 不分点、长度合规 | 规则统计 | 编号 / markdown 比例、自报座位比例、落在篇幅区间内的比例 |
| S2 风格可辨识 | 愿景 1 | 12 个 bot 对同一组局面各自发言；裁判拿 12 张风格卡做匹配；另算向量的类内 / 类间距离 | top-1 识别率（随机水平 8.3%） |
| S3 同质化 | 互相模仿 | 整局里跨座位共用的 n-gram | 共用 6-gram 比例 |
| L1 表达不变性 | 愿景 2 的核心 | 成对题：事实相同，A 版里狼说得长而有条理、真预言家说得短而冲；B 版两边对调 | 站边准确率；表达偏差 = P(信“会说的”一方) − 0.5 |
| L2 琐碎陷阱 | 追不追无关紧要的点 | 两边只在首夜验谁、警徽流先后、措辞上有差别 | 以琐碎点作为主要依据的比例（裁判） |
| L3 核心矛盾 | 能否抓住关键 | 局面里埋一个决定性事实（越位知道刀口、金水反投、自爆带走的人） | 命中率（裁判） |
| L4 真实局面 | 综合判断 | 从存档切出的决策点（如 0fa7 的真预言家对悍跳） | 站边 / 投票准确率 |
| M1 分层消融 | 每层都起作用、可插拔不串味 | 逐层移除或替换 | 该层对应指标显著变化（p < 0.05），其他指标不变差 |
| M2 对局记忆召回 | L3 不被淹没 | 在对局后段提问前期事实 | 召回准确率（压缩前 / 后） |
| M3 规则理解 | L2 规则层 | 规则测验（同守同救、遗言资格、警长投票权……） | 正确率 |
| E1 学习曲线 | 长期迭代 | 固定对手池打 N 局，每局后复盘 | L 套件与胜率随版本的趋势 |
| E2 向人类学风格 | H34 | 采纳风格提案后，裁判两两比较“哪段更像这位玩家” | 胜率，且 S1 仍然合规 |
| G 联赛 | 端到端 | 固定随机种子、身份轮换的整局 | TrueSkill、阵营胜率、好人投票命中率 |

严谨性与成本：

- **基准里的发言也必须由 bot 自己产生**（H18）：runner 用局面脚本建好世界，运行真实的 Agent / Worker 循环，直到 bot 自己调用 `speak` 或 `pass`（或请求作答）为止，记录它的工具调用。不允许用单独的“请写一段发言”提示去直接生成发言。
- 每题采样 k 次，用 bootstrap 给出置信区间；裁判 rubric 固定版本，校准一致性 κ ≥ 0.6 才计入验收（H48）。
- 成本分三档：冒烟（CI，0 次调用）、快速（约 300 次调用）、完整（数千次调用 + 5–10 局联赛）。

初拟门槛（M0 基线后修订）：

- 截断数 = 0；
- 编号 / markdown ≤ 10%，自报座位 ≤ 5%；
- S2 top-1 ≥ 50%；
- L1 表达偏差比基线降低一半以上；
- L2 陷阱命中率不超过基线的一半；
- L4 站边准确率比基线高 20 个百分点；
- M1 每层在自己对应的指标上显著；
- M3 ≥ 90%；
- E1 学 10 局后不退化，且至少一项显著提升；
- E2 胜率 ≥ 65%。

## 7. 风险与已知限制

| 风险 | 应对 |
|---|---|
| bot 自学学到错误结论（v0.13 的复盘就学出了“结构清楚 = 可信”） | 复盘必须对照事后真相；打法带把握度和证据计数，低把握度不挂载；复盘直接生效、不回滚（C9），发现问题时在详情面板直接编辑或清除；基准 E1 监控 |
| 120 秒初始化对思考模型偏紧（单次调用可能 30–60 秒） | 一个回答里并行写多个文件；失败时显示原因、可重试；用时纳入 R 套件；必要时改为可配置 |
| 契约或剧本一改，全部 bot 都要重新初始化 | 先弹窗告知；全局初始化并行进行；这是保证“记忆和来源一致”的代价（C8） |
| 输出闸门和超长退回增加调用次数；bot 反复超长可能拖到发言权超时 | 退回回执写明实际字数和上限，事件提示里也给出上限；`FORMAT` 只退回一次；R 套件统计退回次数与超时率 |
| 学人类风格时把粗口一并学走 | 提案时过滤辱骂性词句；L0 必须经用户确认 |
| bot 之间互相过拟合对方的套路 | 引入人类对局数据；基准题目与学习隔离（H50）；联赛轮换身份 |
| 改名会清空记忆，且不能撤销（C9） | 二次确认，弹窗写明会清空哪些内容；需要保留时先用详情面板导出 `.arenabot` |
| 复盘写坏记忆后不能回滚（C9） | 每次复盘后显示改动摘要；用户可以直接编辑或清除；重要的 bot 可以先导出备份 |
| 存档必须包含全部日志，文件可能很大 | 导出前显示预计大小与进度；沿用流式打包；`ARENA_MAX_ARCHIVE_BYTES` 仍然有效 |
| 拖动交互在触屏和键盘上的可用性 | 长按拖动 + 键盘快捷键；浏览器矩阵覆盖 |
| 局面脚本化（把 ledger 转成可重放的脚本）可能有缺口 | M0 先验证可行性；不可行的局面改用合成题，并在今后对局中捕获决策点 |
