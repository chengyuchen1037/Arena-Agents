# 校准：让人工标注告诉你，裁判靠不靠谱

v0.14 基准里的**裁判**是 DSH 的子 agent（见 [../../README.md](../../README.md) 的“裁判（judges）”一节），不是被测的模型。裁判说“这个决定主要靠决定性事实”“这段发言是 C 卡说的”，
这些话本身要先被检验：**你自己来标一批同样的条目，看看你和裁判是不是一回事。**一致性用 Cohen's κ 算——某个 rubric 的 **κ ≥ 0.6 且至少 20 对**，它的裁判结果才计入验收（H48）；
不够的，报告里只作参考。

整件事在本地完成：不调任何模型，标注页不联网。

```
基准运行 ──► judge_items.jsonl ──► 裁判（DSH workflow）──► judgments.jsonl
                  │                                              │
                  └──► calibration-set ──► set.jsonl ──► 标注页 ──► labels.jsonl ──► calibrate ◄──┘
                                                                                         │
                                                                                  calibration.json ──► bench report
```

## 1. 要标多少条

**每个 rubric 30 条起**——要计入验收的都要标：S2（风格识别）、L1 / L2 / L3（核心逻辑），有用到 E2、M2 的也一样。

- 校准至少要 **20 对**（人工和裁判都有的条目，`--min-n`）；标 30 条，是给“这条我没法判，跳过了”和“版本对不上”留余量。
- 条目少于 30 时 κ 的区间很宽：0.65 的点估计，区间可能是 [0.3, 0.9]——这种结果算“通过”，但不稳；能多标就多标。
- 工作量：每条约半分钟到一分钟，四个 rubric 一百多条，一两个小时。进度自动保存，可以分几次标。
- 某个 rubric 的条目不够 30？命令会提示“只有 N 条可抽”并全取。回去多跑几个样本（`python -m bench run --samples …`）再抽。

## 2. 抽样：`calibration-set`

```bash
python -m bench calibration-set --items judge_items.jsonl --judgments judgments.jsonl --n 30 --seed 1 --out set.jsonl
```

| 参数 | 含义 |
|---|---|
| `--items` | 运行目录里的 `judge_items.jsonl` |
| `--judgments` | `judge-merge` 写的 `judgments.jsonl`（可以给几个文件）。给了，就按裁判的取值分层；不给，按 bot × 题分层 |
| `--n` | 每个 rubric 抽几条（默认 30） |
| `--rubrics` | 只抽这几个，逗号隔开：`--rubrics S2,L3` |
| `--seed` | 抽样和排序的种子（默认 1）：同样的输入和种子，得到同样的 `set.jsonl` |
| `--out` | 写到哪里 |

输出例：

```
L3  v1  取了 30 / 147 条  分层（裁判的取值）：decisive_fact 7 · expression 7 · intuition 8 · trivia 8
写到 set.jsonl（共 30 条，顺序已打乱，种子 1）。下一步：用浏览器打开 bench/label/index.html，选择这个文件开始标注。
```

**怎么抽**

- 给了 `--judgments`：只在“有现行版本判定”的条目里抽（没判过的、用旧版 rubric 判的，配不成对，标了也白标）。按裁判在**主指标**（rubric 的 `primary`：L 系列是 `basis`，S2 是 `match`，E2 是 `closer`，M2 是 `recall`）上的取值分层，
  **每种取值都有样本**，数量尽量一样多；某个取值不够，就全取，别的取值补上。取值里面，bot 和题轮流出场。
- 一个 rubric 的样本不受别的 rubric 影响（再加一个 rubric 的条目，这个 rubric 抽到的还是同一批）。
- 所有 rubric 的条目**混在一起打乱**：顺序不会泄露“这条裁判判的是哪一类”。

**盲化**：`set.jsonl` 的每一行是你在页面上看到的全部，和裁判的提示里的内容一样（同一个 `blind_view_of`）：

| 字段 | 内容 |
|---|---|
| `format` `version` | `arena-bench-label-item`、`1` |
| `blind_id` | 这一条的代号（和 `judgments.jsonl` 里的对得上） |
| `rubric` `rubric_version` `title` `kind` `primary` | 哪个 rubric、它的版本、标题、种类、主指标 |
| `schema` | 你要填的格式——就是裁判填的那份 schema（S2 的 `match` / `runner_up` 换成这一条的卡片 id，页面上是按钮） |
| `guide` | 评分标准里“怎么判”的部分（不含示例），页面上折叠显示 |
| `view` | 局面、背景（决定性事实、风格卡、参考发言……）和被评的发言 / 选择 / 理由 |

**没有**：bot、运行、采样、题目 id、真值（哪个是对的）、裁判的判定。抽样时还会检查：`view` 里如果出现了 bot 名、运行 id、题目 id，这一条就丢掉并提示（说明题目的 `title` / `brief` 写漏了）。

> **先标，后看。**标之前不要打开 `judgments.jsonl`，也别看抽样命令打印的取值分布（它是按裁判的取值分层的）——知道裁判怎么判，就会不自觉地往那边标。介意的话，让别人替你跑这条命令。

## 3. 标注：`bench/label/index.html`

用浏览器（新一点的 Chrome / Edge / Firefox / Safari，手机和平板也行）**直接打开这个文件**——不需要服务器，页面**不联网**，也没有外部依赖。

1. 点“选择 set.jsonl”，或者把文件拖到页面上。
2. 一条一条标。页面上从上到下：
   - **背景**：局面的说明；L 系列有“决定性事实”和“容易被带偏的地方”；S2 有“风格卡”；E2 有“这位真人的参考发言”；M2 有“问题”和“标准答案”。
   - **待评内容**：被评的发言、选择、理由、思考；E2 是并排的两段候选 X / Y。
   - **你的判定**：和裁判**同一份格式**。选择题是一排按钮（取值旁边有评分标准里的一句话定义），是 / 否题两个按钮，理由这类文字框可以不填。必填的没选完，不能往后。
   - **评分标准**：折叠着，展开就是裁判看到的“怎么判”。**标之前读一遍。**
3. 标完点“导出 labels.jsonl”（页面里的“标注者”填你的名字，默认 `user`）。可以随时导出，只导出已经标完的条目。

**键盘**

| 键 | 做什么 |
|---|---|
| `←` `→` | 上一条 / 下一条（这一条必填的没标完，`→` 不会往后：先标，或者按 `S` 跳过） |
| `1`–`9` | 选当前高亮的那一题的第几个选项；选完自动跳到下一题 |
| `Y` `N` | 是 / 否 |
| `Enter` | 保存并下一条（文本框里也可以） |
| `S` | 跳过这一条（以后用“下一条没标的”或顶部的“跳到”回来标） |
| `Esc` | 离开文本框 |

**进度**：每改一下，都存在这个浏览器的 localStorage 里；键里带着 `set.jsonl` 内容的指纹，所以**换一个文件不会串**，同一个文件再打开会接着标。
清除浏览器数据、换浏览器、无痕窗口，进度就没了——所以标完一批先导出。“清除本地进度”只清当前这个文件的（会先问你）。页面顶部的“已标 x / 共 n”是进度条。
明暗主题默认跟着系统，也可以点“主题”手动切换。页面不显示、也不保存 bot 名和 `item_id`（`set.jsonl` 里本来就没有）；存下来的只有你的答案和 `blind_id`（一个哈希代号）。

## 4. 校准：`calibrate`

```bash
python -m bench calibrate --labels labels.jsonl --judgments judgments.jsonl --out calibration.json
```

| 参数 | 含义 |
|---|---|
| `--labels` | 标注页导出的 `labels.jsonl`（可以给几个文件：分几次导出的，一起算） |
| `--judgments` | `judge-merge` 写的 `judgments.jsonl` |
| `--min-n` | 至少几对才计入（默认 20） |
| `--threshold` | κ 至少多少才计入（默认 0.6）。调高可以更严；调低只是试一试——`bench report` 无论如何都要 κ ≥ 0.6（H48） |
| `--out` | 写 `calibration.json`（`python -m bench report --calibration calibration.json` 读它） |

**怎么配对**：用 `blind_id` 把你的标注和裁判的判定配起来，**只算两边都有的**；配不上的数目会报告。人工标注、裁判的判定、现行的 rubric 三者的 `rubric_version` 必须相同，否则不算（改过 rubric 之后，旧的判定和旧的标注都作废，见下面第 6 节）。
同一条标了两次，取 `ts` 最新的；格式不符合 rubric 的标注 / 判定不计入，并说明。

输出例（先是表，再是没通过的 rubric 的混淆矩阵）：

```
校准：人工标注 ↔ 裁判（κ ≥ 0.6 且至少 20 对才计入验收）
rubric  版本  配对 n  κ        95% 区间           一致率  解读  计入验收  说明
L2      v1        30  -0.1628  [-0.4445, 0.1176]     33%  弱    否        κ 太低（-0.1628 < 0.6）
L3      v1        30   0.7748  [0.5876, 0.951]       83%  够    是        通过（κ 0.7748 ≥ 0.6，n 30 ≥ 20）

L2 的混淆矩阵（行 = 人工标注，列 = 裁判）：
              expression  intuition  trivia
  expression           5          0       9
  intuition            0          0       4
  trivia               7          0       5
  字段 cites_decisive：一致率 100%（30 对）
```

退出码：算出来了是 0（不管通过与否）；一对也没配上、或文件读不了是 1。

`calibration.json` 每个 rubric 一项：

| 键 | 含义 |
|---|---|
| `rubric_version` | 配对时用的 rubric 版本 |
| `n` | 配上的对数 |
| `unpaired_labels` `unpaired_judgments` | 你标了裁判没判的条数 / 裁判判了你没标的条数（后者通常很大：裁判判得比你标得多） |
| `stale_pairs` `invalid_labels` `invalid_judgments` `duplicate_labels` | 因为版本不一致、格式不符、重复而没计入或被替换的数目 |
| `primary` `kappa` `ci` | 主指标、κ、95% 区间（自助法，固定种子：同样的数据同样的区间）。算不出来是 `null` |
| `agreement` | 主指标上的一致率（两边选的一样的比例） |
| `confusion` | 混淆矩阵：`confusion[人工][裁判]` = 条数 |
| `fields` | 其余选择 / 是否字段的一致率和 κ（文字字段不比） |
| `counts_for_acceptance` | `κ ≥ threshold 且 n ≥ min_n`：为 `true` 才计入验收 |
| `reason` | 写明原因：`通过（…）` / `n 太少（…）` / `κ 太低（…）` / `κ 无定义（…）` |

## 5. κ 怎么读

κ 是“比碰运气强多少”：1 = 完全一致，0 = 和碰运气一样，负数 = 比碰运气还差。**不要只看一致率**——一个取值占了八成的 rubric，随便猜都有六成多一致率，κ 会把这部分扣掉。

| κ | 解读 | 怎么办 |
|---|---|---|
| < 0.4 | 弱 | 裁判和你基本不是一回事：先看混淆矩阵 |
| 0.4 – 0.6 | 中 | 有点像，但不够：多半是两三个取值的界线不清 |
| ≥ 0.6 | 够 | 且 n ≥ 20，计入验收 |

- **看区间，不只看点**：点估计 0.62、区间 [0.35, 0.85]，意思是“可能够，也可能不够”。想稳，就多标一些（再抽一批，`--seed 2`），区间会变窄。
- **κ 无定义**：你和裁判都只用了一种取值（比如每条都是 `trivia`）。这批样本分不出好裁判和固执的裁判，不计入。抽样时给 `--judgments`，各种取值都会有样本。
- **n 太少**：不到 `--min-n` 对。多标，或者少跳过。

## 6. 没通过怎么办

1. **先看混淆矩阵**（行 = 你，列 = 裁判）。上面 L2 的例子：你把 9 条标成 `expression`，裁判都判成 `trivia`；你标 `trivia` 的 12 条里有 7 条裁判判成 `expression`。错在**这两个取值的界线**上，而不是随机的。
2. **通常是 rubric 的措辞有歧义。**对着混淆最多的那两个取值，读 `bench/judges/<rubric>.md` 里它们的定义，改清楚：加判例、写明“看哪一句”、“同时出现时以哪个为准”。
3. **改了 rubric，就要改它的版本号**（front matter 里的 `version` 加 1），然后：
   `python -m bench judge-check` → `judge-pack` → 在 DSH 里重新裁判 → `judge-merge`（旧版本的判定会被拒绝）→ 重新 `calibration-set`（`set.jsonl` 变了，页面会把它当成新文件，旧进度不会串进来）→ 重新标 → `calibrate`。
   旧版本的标注和判定在 `calibrate` 里会被当成 `stale_pairs`，不计入——这是故意的。
4. **也可能是你标得不一致。**把评分标准读一遍；确实拿不准的条目，宁可 `S` 跳过。两个人各标一遍更好——但 `calibrate` 现在只比“人 ↔ 裁判”，不比人和人。
5. **还是过不了**：这个 rubric 的裁判结果只作参考（`counts_for_acceptance` 为 `false`，报告里写“未校准 / 仅供参考”），验收时不靠它。

## 7. 常见问题

- **页面没反应 / 白屏**：用较新的浏览器；打开 `index.html` 时同目录要有 `label.js`；按 F12 看控制台。
- **选了文件说“没有可以标注的条目”**：选错文件了。要的是 `calibration-set` 写的 `set.jsonl`，不是 `judge_items.jsonl`（那个里面有 bot 名，页面不收）。
- **换了一台电脑想接着标**：进度在浏览器里，不会跟着走（也没有“导入进度”）。先在原来的电脑导出 `labels.jsonl`；在新电脑上用另一个种子再抽一份（`--seed 2`）接着标，最后 `calibrate --labels a.jsonl b.jsonl` 一起算（两份里碰巧有同一条，取最新的）。
- **想重新开始**：页面里点“清除本地进度”。
